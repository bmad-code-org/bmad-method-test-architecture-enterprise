# Test Suite

The test suite checks schemas, installation, knowledge fragments, release metadata, CLI behavior, and evaluation machinery.
`npm test` runs repository gates and local execution checks without live model calls.

`schema/suite-manifest.js` and `schema/eval-result.js` follow the same idiom: a Zod schema is the source of truth and `tools/validate-eval-schemas.js` is the validator that runs in `npm test`.
The second of those also generates `schema/eval-result.schema.json`, so regenerate it with `node tools/validate-eval-schemas.js --write` after changing the Zod source.

`contracts/` follows that idiom too.
The sixteen eval contracts are generated by `tools/generate-contracts.js` from `fixtures/test-review-eval/ground-truth.json`, `fixtures/test-design-eval/ground-truth.json`, `fixtures/trace-eval/ground-truth.json`, `fixtures/nfr-eval/ground-truth.json`, `fixtures/ci-eval/ground-truth.json`, `fixtures/tea-routing-eval/ground-truth.json`, the criteria registry, and each `evals/<workflow>/evals.json`.
Edit their source files and regenerate them.
`node tools/generate-contracts.js --check` regenerates them in memory and fails when the bytes on disk differ, which is what stops a fixture edit from leaving a contract quietly wrong.
Regenerate with `node tools/generate-contracts.js`.

## Quick Start

On Linux, `npm test` needs `bubblewrap` (`bwrap`) on `PATH`: `test:atdd-isolation` and `test:atdd-net-guard` execute generated Playwright tests under an OS sandbox with no unconfined fallback, and `selectBackend()` exits 2 naming the missing binary and the install command if it is absent. macOS needs nothing extra; `sandbox-exec` ships with the OS.
See `.github/workflows/quality.yaml`'s `chain` job for the exact install step CI runs.

```bash
# Full quality gate (all suites, lint, markdownlint, format)
npm test

# Run with coverage report
npm run test:coverage

# Individual suites
npm run test:schemas           # test-agent-schema
npm run test:install           # test-installation-components
npm run test:cli               # test-test-review-cli
npm run test:knowledge         # test-knowledge-base
npm run test:release-metadata  # test-release-metadata
npm run test:eval-data         # eval-fragment-selection --validate-only
npm run test:eval-nfr-data     # eval-nfr --validate-only
npm run test:eval-ci-data      # eval-ci --validate-only
npm run test:eval-automate-data # eval-automate --validate-only
npm run test:eval-framework-scaffold-data  # eval-framework-scaffold --validate-only
npm run test:framework-scaffold-install-isolation  # test-framework-scaffold-install-isolation
npm run test:eval-test-design-data  # eval-test-design --validate-only
npm run test:eval-trace-data   # eval-trace --validate-only
npm run test:eval-routing-data # eval-bmad-tea-routing --validate-only
npm run test:eval-schemas      # validate-eval-schemas
npm run test:eval-replay       # test-eval-replay
npm run test:contracts         # test-contracts
npm run test:contract-oracles  # test-contract-oracles
npm run test:probe-targets     # test-probe-targets

# Are the eval contracts still what their sources generate?
node tools/generate-contracts.js --check

# Validate actual agent files
npm run validate:schemas
```

## tea-test-review CLI suite

`test-test-review-cli.js` covers `cli/` in isolation. Its header comment lists
every suite it contains. No vendor CLI (`agy`, `claude`, `codex`) is ever actually
spawned here; `fixtures/test-review-cli/stub-agent.js` stands in via
`--agent-cmd` for every adapter's argv shape.

Fixtures live under `fixtures/test-review-cli/`:

- `reports/*.md`: agent reports fed to `parse-report`. Filenames describe the
  case. The reason each one must be rejected is declared inline in the
  `unparseableFixtures` table in the test, so a description cannot drift away
  from the assertion that enforces it.
- `project/`, `project-claude/`, `project-empty/`: project trees for
  `resolve-skill`, covering the `_bmad` layout, the `.claude/skills` layout, and
  no skill installed. The `SKILL.md` stubs are one line each; only their location
  matters.
- `stub-agent.js`: a fake agent for the end-to-end paths. `STUB_MODE` selects one
  of twelve behaviours, including a crash, writing nothing, a stale report, and an
  attempted forbidden write that proves isolation is active. Eight of the modes
  copy a `reports/` fixture as their payload, so those files serve both the
  parser suite and the end-to-end suite.

A fixture report is shaped to the parser, so a green run here proves nothing
about what a live agent emits. `wrapped-steps-flow.md` and `empty-steps-flow.md`
exist because a real run produced a frontmatter shape that every other fixture
had missed; `plain-bullets-key-strengths.md` exists because a real `--agent
codex` run wrote plain `"- "` bullets under Key Strengths/Weaknesses instead of
the `✅`/`❌`-prefixed form `claude` reliably produces; the parser's own
best-effort design already tolerates this, the fixture just pins it down.

## test-design eval suite

`eval-test-design.js` measures `bmad-testarch-test-design` against `fixtures/test-design-eval/`.
The two fixture sets each contain one epic.
The seeded set has five material risks and four ruled-out risks; the clean set has four ruled-out risks and a ceiling of three risks total.
They run in separate disposable workspaces through `tea-test-design-runner` with `scoped-artifact-writes`.

The skill is copied outside the project root so its worked registers cannot be mistaken for project evidence.
The harness compares repository state before and after every run and refuses to score a run that changed it.

Ten measurements check the generated design:

| Measurement       | Check                                                  |
| ----------------- | ------------------------------------------------------ |
| Grounding         | Risk category and deciding token groups match the epic |
| Precision         | Reported risks avoid explicitly ruled-out risks        |
| Scale             | Probability and impact are integers from 1 to 3        |
| Arithmetic        | Score equals probability × impact                      |
| Category          | Each category is one of the six declared categories    |
| Risk IDs          | IDs are unique `R-NNN` values                          |
| Band placement    | Each score fits its stated heading range               |
| Links             | Coverage rows reference declared risk IDs              |
| Coverage          | Each material risk reaches an admitted test level      |
| Priority ordering | Fixture severity ranks preserve relative priority      |

The seven arithmetic and vocabulary checks gate at 1.
Grounding, precision, and coverage mapping gate at 0.8 because token matching can miss valid wording.
Priority is a separate judgment informed by risk and other factors; the suite checks the fixture's relative ordering.

`--validate-only` checks quotation spans, matcher independence, staged context, and ground-truth exclusion without a model call.
It reports 2 fixture sets, 5 material risks, 8 ruled-out risks, and 9 ordering constraints.

## trace eval suite

`eval-trace.js` measures `bmad-testarch-trace` against `fixtures/trace-eval/`.
The seeded and clean sets run separately, each with its own oracle and gate.

The harness stages the fixture, resolved config, and skill, then invokes `tea-trace-runner` through the command adapter.
It reads `e2e-trace-summary-{run_key}.json` and `traceability-matrix-{run_key}.md` from `test-artifacts/trace/`, using `epic-{epic_num}` as the run key.
The 0.3.x summary carries deterministic counts and gate fields.
Per-criterion coverage status comes from the matrix.

The seeded workspace carries its own live-verification input and waiver register.
The clean workspace starts with an empty artifact directory so it cannot inherit them.

`--validate-only` checks ground-truth spans, recomputed coverage counts, derived gates, and context exclusion.
Pinned skill citations that have moved produce drift notices.

## bmad-tea routing suite

`eval-bmad-tea-routing.js` checks routing against the agent's ten workflow menu items.
The corpus has nineteen intents: eleven with one correct route, four requiring clarification, and four unsupported requests.
`intents.json` is shown to the agent; `ground-truth.json` stays outside its context.
Prompt checks detect ground-truth bytes and hidden keys before a model call.

Expected menu codes must exist in `customize.toml`.
The ambiguity table in Step 8 must agree with each case's facts, supported codes, and missing deciding information.
`test:eval-routing-boundaries` checks missing, duplicate, orphaned, and drifted rows.
Stored replays cover all four clarification branches and a direct review request routed to `RV`.

Five metrics measure route accuracy, reason grounding, scope preservation, clarification, and rejection of unsupported requests.
Zero-ceiling controls catch confident unsupported routes, confident ambiguous routes, and clear intents left unrouted.
Reason matching uses deciding tokens from the user's own message.
The generator and scorer share the pattern rule; `cli/lib/parse-routing.js` parses the reply.

Two contracts cover the suite because AD-39 limits a plan to sixteen steps.
The intents contract contains eleven routes and the controls contract contains eight clarification or decline cases.

## scorer replay suite

`test-eval-replay.js` runs the live parsers and scorers over stored outputs without model calls or network access.
Cases live under `replay/<suite>/<case>/` with their outputs and an `expected.json` derived by hand.

The 158 cases include fifteen trace pairs, twenty-nine NFR reports, and fifty-four CI runs.
They cover valid outputs, misleading findings, missing or malformed artifacts, wrong gates and counts, fabricated citations, quoted examples, and fixture mutations.
Each case records the scoring-input digest and whether its bytes were captured or constructed.

`signatureOf` must change when a scored result changes.
The NFR grounding pair signs differently despite equal status totals because its evidence differs.
The CI Node-version pair signs identically because a matching literal and `.nvmrc` reference score identically.

A changed result at the same `SCORER_VERSION` fails.
Bump the version deliberately before `--accept` updates only the cases whose results moved.

Of 158 cases, 152 produce a number and 134 of those are constructed.
21 CI replays cover the full and minimal projects.
Eighteen carry captured bytes: twelve ATDD corpus reports, two CLI fixtures, and four live CI runs for `evaluation-plan`, `evaluation-tiers`, `evaluation-edit`, and `evaluation-gate`.
The two review captures score zero recall because they report no findings.
All routing replays are constructed; `test:eval-routing-evidence` checks live Story 1.3 evidence separately.

The suite also runs credential-free checks for `test/lib/eval-record.js`.
Constructed replay cases establish scorer regression behavior; recorded live evidence establishes how the skill performed.

## nfr eval suite

`eval-nfr.js` measures `bmad-testarch-nfr` against separate gapped and clean bundles under `fixtures/nfr-eval/`.
Each bundle has its own service and thresholds.

The gapped bundle offers a healthy load report with no performance target and a coverage claim with no coverage report.
Both domains require CONCERNS; `maxUnsupportedPass` has a zero ceiling.
The clean bundle supports four PASS results.

`tea-nfr-runner` writes `nfr/nfr-assessment-system.md` for these system-level fixtures.
The harness reads each domain's status from the Gate YAML `audited_domains` block and compares it with the domain's assessment section.
Missing, repeated, unreadable, or contradictory domain answers fail their declared checks.
Fenced examples are removed before parsing assessment prose; the Gate YAML is read separately as a fenced artifact.

Citation accuracy requires real files from the bundle.
`groundedCitationAccuracy` additionally requires every cited file to match that criterion's declared evidence.
A correct citation alongside an incorrect one fails grounding for that criterion.
Uncited criteria and criteria with no declared evidence are excluded from that metric.

The grounding threshold of 1 was calibrated with Claude over four repetitions of both bundles.
It has no Codex or Gemini calibration in that record.
`--validate-only` checks cited workflow rules and fixture spans.

## ci eval suite

`eval-ci.js` measures `bmad-testarch-ci` against six independent Node projects in `fixtures/ci-eval/`:

| Project            | What it checks                                                          |
| ------------------ | ----------------------------------------------------------------------- |
| `full`             | Thirteen requested production-pipeline elements                         |
| `minimal`          | Five requested elements with extras explicitly forbidden                |
| `evaluation-plan`  | Detect a plan and render the PR tier                                    |
| `evaluation-tiers` | Render PR, merge, scheduled, and release jobs with correct event guards |
| `evaluation-edit`  | Replace the marked job and preserve the handwritten job and checkpoint  |
| `evaluation-gate`  | Add the release evaluation to a publish job's existing `needs`          |

Every project carries `docs/ci-requirements.md` and runs in its own workspace.
The four evaluation projects have real captured replays; `test:evaluate-ci-render` covers deterministic rendering.

The suite parses `.github/workflows/test.yml` with strict YAML and runs `actionlint` using pinned flags.
Parse and lint ceilings are zero.
Structural checks cover triggers, permissions, commands, job dependencies, sharding, burn-in, uploads, runtime versions, event guards, timeouts, preserved jobs, and checkpoints.
It also checks unrequested elements, unsafe context interpolation, and suppressed test failures.
Evaluation artifacts use `if: always()`, one unique name per job, and tier-specific 30- or 120-minute limits.

The agent has no shell in this suite.
Its prompt requires local command preflight checks to be recorded as unexecuted.
The suite does not establish that the fixture's own tests pass.
Actionlint's minimum and actual version travel with the run record.

## automate eval suite

`eval-automate.js` executes four hand-authored Playwright sets against `fixtures/automate-eval/voucher-service`.
It makes no model call.
Both the default invocation and `--validate-only` run the full cycle; `--preflight-only` checks tool and corpus availability.

Each set runs against the fixed service and a scratch copy whose minimum-spend comparison changes from inclusive to exclusive.
`correct-run` tests the exact boundary and must fail on the mutation with the declared signature.
`misses-regression` tests interior values and misses it.
`vacuous-pass` contains an assertion that every response satisfies.
`duplicate` repeats coverage under another title.
The last two properties are checked in source before either server starts.

The suite declares `contracts: []` because it has no shipped generation command for a contract to invoke.
Its fragment-selection contract covers knowledge routing.

## framework-scaffold eval suite

`eval-framework-scaffold.js` installs and executes the committed scaffold fixture without invoking an agent.
`test-framework-scaffold.js` separately checks the scaffold's static structure.

The suite copies `fixtures/framework-scaffold/clean/` into a disposable workspace, replaces the unknown-auth `TODO`, and selects an installable utility version.
It runs `npm install`, then the API sample against `lib/framework-scaffold-stub-server.js`, under NFR9 isolation.
The UI sample requires Chromium and stays outside this suite's scope.

`lib/framework-scaffold-install-isolation.js` supplies a loopback CONNECT proxy that permits only `registry.npmjs.org:443`.
The sandbox reaches it through `HTTPS_PROXY`.
Isolation checks verify denied hosts, allowed loopback access, and a positive proxy control, including child processes.
Those checks need no external network and run in `npm test`.

Two mutations run against the installed workspace:

- Wrong backend `createStatus` must fail with `Received: 500`.
- Removing `authFixture` from `mergeTests(...)` must fail with `unknown parameter "authToken"`.

The thresholds are `installAndSmokePassRate` and `seededDefectDetectionRate`, with one repetition.
Agent-selection flags are accepted for `eval:all` argument compatibility.

## contract oracle suite

`test-contract-oracles.js` evaluates every oracle in every contract under `contracts/` with `eval-quality`'s own evaluator and compares each answer with the harness scorer's on the same evidence: every stored `test-review` verdict is one observation of the contract's `review-corpus` step, every fragment-selection case is evaluated over three constructed selections plus the stored captures, and every stored `test-design`, `trace`, `nfr` and `ci` run is one observation of its own set's or bundle's plan step, evaluated under both of that suite's sets so each oracle is also seen resolving false.
The `ci` contract's two evaluation-command oracles and its burn-in oracle are also evaluated over constructed forms of the lines they read, forty-one forms of the two commands and 232 of the burn-in job.
The two `bmad-tea-routing` contracts are evaluated the same way, over a correct and a failing answer constructed for every intent plus the seventeen stored replies, and each of their oracles has to be seen resolving false on some answer as well as true on another.
An oracle that faults, or that holds where the scorer fails, or fails where the scorer holds, fails the suite.
Its first run found that every regex oracle in `test-review.contract.json` was refused by the evaluator as a catastrophic-backtracking shape, which `compile` never checks.
The one admitted divergence is AD-4's reading of an empty collection, recorded in `contracts/README.md`.

## preflight

Each eval harness accepts `--preflight-only` beside `--validate-only`.
The first runs the static checks and then probes the runner: the executable is on `PATH`, answers `--version`, and a built-in vendor has a credential.
It exits before any model call, and it is what `eval:all --preflight-only` passes each suite through the manifest's `preflightArgs`.
`tools/validate-eval-schemas.js` runs that argv once with a missing runner and once with `node` standing in as a custom runner, and both the exit code and the result record have to match, so a preflight that stops reaching the runner fails `npm test`.

## Live evaluations

A live evaluation launches an authenticated agent CLI headlessly and scores its response. From the repository root, run one built-in adapter or the complete matrix:

```bash
npm run eval:all -- --agent codex
npm run eval:all -- --agent claude
npm run eval:all -- --agent agy
npm run eval:all -- --agent agy --agent claude --agent codex
```

Preflight checks the corpus, executable, version, credentials, and execution tools without a model call:

```bash
npm run eval:all -- --agent codex --preflight-only
npm run eval:all -- --agent claude --preflight-only
npm run eval:all -- --agent agy --preflight-only
```

`nothing measured` is the expected result. A successful preflight establishes that the setup is usable; the later live call still has to authenticate and complete.

### Focus one suite or skill

```bash
# One review measures recall and false positives; repeated runs also measure stability.
npm run eval:test-review -- --agent codex --runs 1
npm run eval:test-review -- --agent codex
# One trace per fixture set, or just the named fixture set.
npm run eval:trace -- --agent codex --runs 1
npm run eval:trace -- --agent codex --set seeded-tenant-data-export
npm run eval:nfr -- --agent codex
npm run eval:ci -- --agent codex
npm run eval:test-design -- --agent codex
npm run eval:atdd -- --agent codex
npm run eval:teach-me-testing -- --agent codex
```

Fragment selection accepts a workflow ID. These examples run one repetition; use `--runs 2` for stability measurement:

| Skill       | Command                                                                                          |
| ----------- | ------------------------------------------------------------------------------------------------ |
| ATDD        | `npm run eval:fragment-selection -- --agent codex --workflow bmad-testarch-atdd --runs 1`        |
| Automate    | `npm run eval:fragment-selection -- --agent codex --workflow bmad-testarch-automate --runs 1`    |
| CI          | `npm run eval:fragment-selection -- --agent codex --workflow bmad-testarch-ci --runs 1`          |
| Framework   | `npm run eval:fragment-selection -- --agent codex --workflow bmad-testarch-framework --runs 1`   |
| NFR         | `npm run eval:fragment-selection -- --agent codex --workflow bmad-testarch-nfr --runs 1`         |
| Test design | `npm run eval:fragment-selection -- --agent codex --workflow bmad-testarch-test-design --runs 1` |

Each record captures the commit, suite/case IDs, runner/version/model, parameters, fixture/prompt digests, expected and completed repetitions, measurements, duration, and failure class. Its schema is validated before writing.

### Custom runner contract

Use `--agent custom` and an explicit `--agent-cmd`. The runner must read the complete prompt from stdin, run non-interactively in the staged working directory, print its final response on stdout, and exit nonzero on failure. Artifact-writing suites also require it to write the paths named in the prompt.

For an installed and authenticated [Gemini CLI](https://geminicli.com/docs/cli/headless/):

```bash
npm run eval:all -- \
  --agent custom \
  --agent-cmd gemini \
  --agent-arg -p \
  --agent-arg "Follow the complete instructions from standard input." \
  --agent-arg --output-format \
  --agent-arg text \
  --agent-arg --approval-mode \
  --agent-arg yolo \
  --agent-arg --skip-trust \
  --env-pass GEMINI_API_KEY \
  --env-pass GOOGLE_API_KEY
```

`yolo` permits the artifact writes these suites require. Fragment selection alone can use Gemini's `plan` approval mode. Pass environment credentials with `--env-pass`; stored CLI logins use the home directory passed by the harness. Supply a custom model flag and value through repeated `--agent-arg` options.

### Thresholds and result handling

The [suite manifest](./evals/suite-manifest.json) owns the full threshold set. `test:eval-schemas` checks that harness constants agree with it. Key thresholds are:

| Suite              | Required measurements                                                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fragment selection | Required recall ≥90%, forbidden selection ≤10%, stable repeated choices                                                                                       |
| Test review        | Recall ≥70%, CRITICAL recall 100%, non-false-positive rate ≥80%, score standard deviation ≤3, stable verdict                                                  |
| Trace              | Criterion accuracy and citation precision ≥90%; gate, arithmetic, oracle, waiver, and live-evidence checks 100%; no clean false positives or fixture mutation |
| Routing            | Route accuracy ≥90%, reason recall ≥80%, scope fidelity ≥87.5%, clarification and decline recall ≥75%; no confident unsupported/ambiguous route               |
| NFR                | Domain accuracy ≥87.5%, threshold fidelity ≥90%, undecidable domains/overall status/domain coverage 100%; no unsupported PASS or fabricated evidence          |
| CI                 | Requested-element recall ≥97%, trigger accuracy 100%, no parse/lint failures, unrequested elements, rule violations, instability, or fixture mutation         |
| Test design        | Grounded recall, precision, and coverage mapping ≥80%; risk arithmetic, bands, categories, IDs, links, and priority ordering 100%                             |
| ATDD               | Red-for-intended-reason rate and criterion coverage 100%; no vacuous pass, skipped test, load error, unmapped test, or production mutation                    |

Every declared repetition must complete. Exit `0` means thresholds passed, `1` means a measured result missed a threshold, and `2` means the environment could not measure the result. A lost call receives no score.

Only the clean review fixture establishes a definite false positive. Unmatched seeded-fixture findings are recorded as `unattributed`, because they may describe an incidental defect.

Run credential-free repository checks on pull requests. Run live evaluations in scheduled or manually triggered jobs with an authenticated runner, and archive their JSON evidence. Live jobs consume model quota.
