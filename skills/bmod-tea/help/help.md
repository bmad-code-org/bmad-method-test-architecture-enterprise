# Test Architect knowledge

This document covers the skills of the `tea` module: what each one gives the user, when to recommend it, where it fits in the method's flow, and what to offer next. Full documentation: <https://bmad-code-org.github.io/bmad-method-test-architecture-enterprise/llms.txt>

## The skills

- `bmad-tea`: Murat, the Master Test Architect, for risk-based test strategy, fixture architecture, API, UI, mobile and contract testing, and release gates. Recommend him when the user wants testing advice or does not know which TEA workflow fits; he routes to the rest.
- `bmad-tea-teach-me-testing`: teaches testing fundamentals in 7 sessions (TEA Academy), with a progress file, session notes and a completion summary. Recommend it to someone learning testing, at any point.
- `bmad-tea-test-design`: risk-based test planning, producing a test design document. At system level it reads the PRD and architecture; at epic level it plans one epic of the active initiative. Recommend it once requirements exist and before tests or a framework do. Afterwards offer `bmad-tea-framework`.
- `bmad-tea-framework`: owns production-ready framework and CI setup, with framework-only, CI-only, or both scope. It installs Playwright Utils or Pact.js Utils when enabled. Recommend it after test design, before the first story is built. When CI scope cannot be inferred from the request, interactive runs ask whether to include CI. Unattended runs default to framework only and state in the summary that CI was excluded.
- `bmad-tea-automate`: owns test generation in red or expand mode. Red mode writes failing acceptance tests and an ATDD checklist for one story before it is built, then verifies the intended missing behavior. Expand mode writes tests for implemented code, runs them, heals test defects for up to three rounds by default, and reports product defects. Recommend red mode once a story's criteria are settled and expand mode once code exists.
- `bmad-tea-evaluate`: builds and runs a scored, evidence-backed evaluation of an agent, skill, workflow or tool-use system. Recommend it after automation when the target's behavior needs proof. Afterwards offer `bmad-tea-framework` with CI scope to enforce it. On explicit request, Evaluate also analyzes saved native Test Design consistency offline or prepares a bounded fresh/configuration proposal. “Is it repeatable?” first clarifies saved records versus new runs. Native live experiments remain blocked by telemetry and enforceable-budget gaps; ordinary evaluation gains no extra experiment work.
- `bmad-tea-test-review`: audits test quality with a 0-100 score and a review report. Recommend it after tests are written. Afterwards offer `bmad-tea-trace`.
- `bmad-tea-nfr`: audits the evidence for non-functional requirements and writes an NFR report. Recommend it after automation, before a release.
- `bmad-tea-trace`: maps requirements to tests in a traceability matrix and makes the PASS, CONCERNS, FAIL or WAIVED gate decision. Recommend it after test review, for the release gate.

For a release gate, the order is: `bmad-tea-test-review` (optional), `bmad-tea-nfr` (optional), then `bmad-tea-trace`.

## Where TEA fits in the method's flow

TEA works on its own. When the method module is installed too, these routes add testing to its flow. Name a method skill only when it is installed, and a TEA skill only when it is installed; otherwise give the route without the missing step, and say which TEA skill would fill it once installed. Depth follows risk: a small, low-risk change needs none of this beyond the checks its build runs.

| The user is                                                                                              | Recommend                                                                                              | Because                                                                                                                                                                                                                                                                  |
| -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Planning an initiative whose risk, compliance or reach calls for a test strategy                         | `bmad-tea-test-design` at system level, once the PRD and architecture exist                            | Testability concerns reach the architecture while it can still change.                                                                                                                                                                                                   |
| About to build the stories of an epic                                                                    | `bmad-tea-test-design` at epic level, then `bmad-tea-framework` when the project has no test framework | The epic's plan sets priorities for every story in it.                                                                                                                                                                                                                   |
| About to build one story with settled criteria, and wants test-first work                                | `bmad-tea-automate` in red mode, then `bmad-build`                                                     | The builder turns the red tests green; the checklist lists them for the story's plan. Red mode takes the story's ref (`1.2`), its title, or its leaf file, and reads the ticket through the method's ticket tools; on v6 it takes the story file.                        |
| Done with `bmad-build` and wants a maintained test suite for the work                                    | `bmad-tea-automate` in expand mode                                                                     | It writes tests that follow the project's framework and fixtures, runs them, and heals test defects. `bmad-qa-generate-e2e-tests` remains the fit for a quick, one-off set of end-to-end tests.                                                                          |
| Upgraded a v6 project with `bmad migrate method` and has TEA checklists, matrices or reports from before | `bmad migrate tea`, after the method migration                                                         | It moves each story output onto its v7 ticket's key from exact evidence, keeps historical citations, and lists anything it cannot map.                                                                                                                                   |
| Has `bmad-tea-atdd` or `bmad-tea-ci` customizations, or `bmad setup` cleanup listed them as unused       | `bmad migrate tea` (migration 3), before cleanup when you can                                          | It moves red settings into `[workflow.red]` of `bmad-tea-automate.toml` and CI settings into `[workflow.ci]` of `bmad-tea-framework.toml`, reading the cleanup backup when cleanup already removed a file. Keep the `.v6-v7-migration-backup-*` folder until it has run. |
| Has tests whose quality is in doubt                                                                      | `bmad-tea-test-review`                                                                                 | A scored audit names the flaky, slow or weak tests.                                                                                                                                                                                                                      |
| Closing an epic or preparing a release                                                                   | The release-gate order above                                                                           | Trace gives the gate decision; Test Review and NFR are added when risk calls for them.                                                                                                                                                                                   |

The story's status is never TEA's to change. Red mode hands its tests to the builder, the builder records the work in the story's plan, and the user or an orchestrator marks the ticket done.

## Where things land

Every workflow writes under the test artifacts folder, chosen at setup as `modules.tea.test_artifacts`, which can sit outside the output folder. To see what TEA has run, resolve it with `uv run {project-root}/_bmad/scripts/resolve_config.py --project-root {project-root} --key modules.tea.test_artifacts` and look in these folders inside it:

| Folder                               | Written by                                                                                                                  |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| `test-design/`                       | `bmad-tea-test-design`: `test-design-epic-<n>.md`, or `test-design-architecture.md` and `test-design-qa.md` at system level |
| `framework/`, `ci/`                  | `bmad-tea-framework`                                                                                                        |
| `atdd/`                              | `bmad-tea-automate` red mode: one `atdd-checklist-<story>.md` per story                                                     |
| `automate/`                          | `bmad-tea-automate` expand mode                                                                                             |
| `test-review/`                       | `bmad-tea-test-review`                                                                                                      |
| `nfr/`                               | `bmad-tea-nfr`                                                                                                              |
| `trace/`                             | `bmad-tea-trace`: one `traceability-matrix-<scope>.md` per story, epic, release or hotfix                                   |
| `evaluate/`                          | `bmad-tea-evaluate` working state                                                                                           |
| `tea-academy/`, `teaching-progress/` | `bmad-tea-teach-me-testing`                                                                                                 |

A file there shows a workflow ran, not that its work is finished: a file whose frontmatter says `workflowStatus: 'in-progress'` is a started run the user can resume.

Runs before these folders existed wrote to the root of the test artifacts folder, and the workflows still read those files: `test-design-epic-<n>.md`, `test-design-architecture.md`, `test-design-qa.md`, `test-design-progress.md` and `test-design-progress-<scope>.md`, `framework-setup-progress.md`, `ci-pipeline-progress.md`, `atdd-checklist-<story>.md`, `automation-summary.md`, `test-review.md`, `nfr-assessment.md` and `traceability-matrix.md`. Read them the same way: the name or heading gives the scope, and only a checkpoint, the report's own status, its content or the user settles whether that run finished. When a root file and a folder file cover the same scope, say both exist and let the user pick. Evaluate writes evaluation folders under `evals/` by default; a team changes that with `evaluations_folder` in `_bmad/custom/bmad-tea-evaluate.toml`. `bmad setup tea` shows and changes the setup answers.
