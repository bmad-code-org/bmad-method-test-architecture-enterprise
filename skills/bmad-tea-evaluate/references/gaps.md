# Gaps

Read the scored development evidence artifact for CONCERNS, FAIL, Invalid or a weak strength vector. Name the first unsatisfied engine rule no contract waiver covers (a `coverageGaps` entry whose `waiverId` is `null`), failed preflight check, missing evidence, or loose oracle. For a development `score` exit 3 with no evidence artifact, read the persisted `runs/<invocationId>/scores/<scoreInvocationId>/<probeId>/score.json` record and its stdout and stderr diagnostics. Treat the exit as a routing fact and read engine evidence for the quality judgment. Read development `interpretation.json` for citations and phase; eval-quality remains the only verdict and strength authority. For a held-out score failure, read only its `gap-view.json` row. An `outcome: null` leaves the held-out cause undisclosed. Hold the held-out loop, author a development probe of the same class, and diagnose its development evidence or score diagnostics; record a blocked gap if the fault cannot be reproduced there.

## Open the report with an evaluation brief

Start `{test_artifacts}/evaluate/<evaluationId>/gap-report.md` from `assets/gap-report.template.md`. Its first section, `## Evaluation brief`, tells a reader who has not seen the evaluation, in plain words: what was tested, the verdict and what it means, what was caught and what was not, the limits, the next step, and links to the run, score and CI artifacts. Fill it last, after the gaps below are recorded, and refresh it after every rescore. Copy each verdict, count and rate from eval-quality's artifacts and compute none. Name held-out results only as `gap-view.json` gives them.

The three sections after the brief report the target itself: `## What the target got wrong` (each target finding's summary in plain words), `## Improvement opportunities` (every finding of `target-findings.json` with its source, evidence, target artifact, proposed change and disposition) and `## Net improvements` (each applied change with its before and after numbers, copied from the two scored runs). Write them from `target-findings.json`, and write "None found" under each when the file records an empty list.

## Classify before repairing

Every failure or weakness is either an instrument problem or a target problem. Decide which before choosing a repair, and record the classification and its reason in the gap report.

- **Instrument problem:** the probe, oracle, rubric, judge calibration, registry, adapter or harness is wrong, so the evaluation misreads correct behavior or misses a defect. The rest of this guide repairs it: the outcome, discipline, preflight, isolation and exit tables below, and the author, rerun and rescore loop.
- **Target problem:** the evidence shows the target itself doing the wrong thing, or the right thing inconsistently, wastefully or beyond its task. Leave the instrument as it is, since tuning a probe or oracle to accept the behavior would hide the defect, and record a target finding as the next section describes.

The test: would a correct target pass this probe as written? If it would, and the target fails, the target is at fault. If a correct target would fail too, the instrument is. When the evidence supports both readings, ask the adopter which behavior the requirements intend, then classify.

These evidence kinds point at the target. `npm exec --prefix {tea_evaluations_folder} -- tea-evaluate target-findings --evaluation <evaluation-folder> --run <invocationId>` lists every candidate one run's evidence holds, with its source and evidence filled from the run and its behavior and severity from the contract; it writes nothing and decides nothing. Confirm each candidate in the cited records before classifying, since each can also come from an instrument fault:

| Evidence                                                                                                                                                                                                                                       | Target finding `source` | Instrument fault to rule out first                                                    |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------- | ------------------------------------------------------------------------------------- |
| A clean control on correct-looking input that `score` fails in every trial (eval-quality exit 2, `false-positive`), or whose qualification baseline fails so `run` stops at exit 11 with `qualification/<probeId>/baseline-pass.json` violated | `clean-control-failure` | An oracle that rejects valid behavior, or input the requirements do not call correct. |
| A behavior that fails only some trials (`outcome.trialVotes` split, such as a clean control failing 1 of 3)                                                                                                                                    | `intermittent-behavior` | A judge or oracle that reads the same output differently across trials.               |
| A behavior the target fails on a probe that is no clean control: a historical probe whose fixed revision still fails, or a held-out probe whose `gap-view.json` row shows failing votes                                                        | `behavior-failure`      | A probe whose route or mutation, rather than the target, makes it fail.               |
| An `observedMounts` path outside the trial set's allowlist that the target opened beyond its task (`## Map an isolation violation to its repair`)                                                                                              | `isolation-violation`   | A toolchain or cache path the registry entry should declare in `systemPaths`.         |
| A `process` finding in `interpretation.json` whose outcome is right and whose steps are wrong or wasteful                                                                                                                                      | `process-finding`       | An operation phase or oracle pointer that misnames the step.                          |
| A rule the target never states, or states two ways, found while authoring requirements (Stages 1 to 3)                                                                                                                                         | `authoring`             | A requirement the adopter has not confirmed; confirm it first.                        |

A rare clean-control failure is evidence even when a rerun passes. Example: a skill's clean control fails one execution in sixty because SKILL.md never says where the reply-format request goes relative to the closing address. Read the failing output against the requirements: the output is wrong and the oracle is right, so record a `clean-control-failure` citing that run's qualification record (or an `intermittent-behavior` citing its scored trials), keep the oracle, and fix SKILL.md at the decision point.

The same test holds for every target kind. Only the artifact a fix lands in changes:

| Target kind            | Where a target fix usually lands                                              |
| ---------------------- | ----------------------------------------------------------------------------- |
| Skill or agent         | `SKILL.md`, the agent's prompt or instructions, or a reference file it loads. |
| MCP tool server        | Tool descriptions, input or output schemas, or the tool handler.              |
| HTTP API or AI feature | The handler, its validation, or the prompt or model configuration behind it.  |
| Workflow               | The step file or the routing between steps.                                   |
| Tool-use system        | The tool descriptions the agent reads, or the agent's tool-choice rules.      |
| promptfoo target       | The prompt or provider configuration the suite runs.                          |
| Test-review mechanism  | The rule, pattern or report logic that judged the test.                       |

## Record target findings

Record every target finding in `<evaluation-folder>/target-findings.json` as soon as it is classified, from Stage 1 onward, with disposition `undecided`. Never stop the loop to fix the target: target findings wait for the one decision point at the end of this stage, and the instrument repairs go on. The runtime's `cli/lib/evaluate/schemas/target-findings.schema.json` defines the file, and `tea-evaluate check` holds it to the folder. Each entry has:

- `id`: `T-001` onward, in order;
- `summary`: what the target got wrong, in plain words;
- `source` and `evidence`: the source kind from the table above and what it cites, as `tea-evaluate target-findings` drafts it. `clean-control-failure` cites `run`, `probe` and either `score` (with the failing `trials`) or `qualification` (`baseline-pass`, the record of a run that stopped at exit 11); `intermittent-behavior` cites `run`, `score`, `probe`, the failing `trials` (record numbers of `trial-sets/<probeId>/record-<n>.json`) and the `trialCount` that ran; `behavior-failure` cites `run`, `score`, `probe` and the failing `trials`; `isolation-violation` cites `run`, `probe` and the `paths` outside the allowlist; `process-finding` cites `run`, `score`, `probe`, its `trials` and the `finding` ID (`F-001`); `authoring` cites the `record` (`requirements.md`, `authoring-log.md` or another file of the folder) and an `excerpt` of its exact words;
- `behaviorId` and `severity`: the contract behavior and the contract's `low`, `material` or `critical`; `behaviorId` is `null` only for an authoring finding no behavior states yet;
- `target`: the `artifact` a fix lands in, relative to `launch.root`, and the proposed `change`;
- `disposition`: `undecided` until the adopter decides.

Cite a held-out probe by its `gap-view.json` row alone: `run`, `score`, `probe` and `gapView` (its `probeClass`, `caught`, `caughtCount`, `validCount` and the trial states as `votes`). Its trials, paths and interpretation stay closed. When a development probe reproduces the failure, add it under `reproducedBy` with its run, score and failing trials. `check` reads every citation against the run it names when that run is on disk (its run directory, or `baseline/` for the accepted run): each cited trial's state, the gap-view row, the qualification verdict, each path against the allowlist, and each process finding rebuilt from the sealed records. An evaluation that found nothing to improve records `"findings": []`, so "no improvements" is an explicit state.

While the loop runs, `check` warns about what is not ready for the pull request and keeps its exit: a scored evaluation with no file, an `undecided` finding, a `this-pr` finding with no `measurement`, and a citation whose run is on neither path. `check --ready`, the pre-PR check, reports the same items as findings and exits 10.

## Read the strength vector

The vector's denominator is unique qualified probe IDs exercised per class, after each probe's trials are reduced. An admitted probe that was not exercised contributes no denominator; its class rate is `null` if none were exercised. `tea-evaluate score` invokes eval-quality once per probe, so one evidence artifact reports only that probe's class component in `defect`, `gameability` or `zero-action`. `caughtCount / validCount > catchThreshold` alone decides whether that probe is caught. Separately, fewer completed trials than `minimumTrialCount` make its strength non-comparable. The class-wide reading is the aggregate the same invocation copies to `strength-aggregate.json`, which eval-quality's `aggregate-strength` stage mints from those artifacts. Per class it states `eligible`, `exercised`, `caught`, `rate`, `comparable` and the floor decision with its `basis` against the adopter's `evaluation.json.strengthFloor`. Copy those readings and compute no rate or decision. A class with no declared floor reads `undeclared` with basis `no-floor-declared`. Under a declared floor the first match wins, in this order: `no-eligible-probe` (a `null` class has no eligible probe), `not-comparable` (`comparable: false`: fewer trials than `minimumTrialCount` or an oracle unreached), `no-exercised-probe` (`rate: null`: eligible probes and none exercised), `unexercised-probe` (some eligible probe never exercised). None of these is a pass. Only a class that clears all four reads `rate-below-floor` or `rate-meets-floor` from its rate. Clean controls and canaries test false positives and viability; they never enter a denominator. When the `strengthAggregate` pointer's `status` is `absent`, `refused`, `mismatch` or `failed`, no aggregate stands and no class-wide claim does either: read the pointer's reason, repair that cause and rescore. One `caught` defect proves only that one detection, not a strong contract. Example: a qualified defect probe catches two of five valid trials at `catchThreshold: 0.5`. The strict rule misses that probe; inspect its three uncaught trial observations, tighten the oracle and rerun development. The artifact's defect component describes that probe alone, and the aggregate's describes the class.

## Read a loose oracle

A gameability probe gives a degenerate answer such as "always decline" or a success keyword with no required action. If it fails qualification or does not resolve `caught`, read the oracle's evidence pointers and check tree. Example: an oracle that looks only for "declined" in stdout will accept a refusal for every request. Add a clean control requiring a legitimate approval and an oracle condition that observes the actual reservation decision and tool call. Requalify the gameability probe and rescore; never manufacture a catch in TeA.

## Separate process from outcome

In `interpretation.json`, `process` and `outcome` list findings by the operation phases captured at run time. Every citation names its `interfaceId` beside its `operationId`, because two interfaces may declare one operation ID and each carries its own phase. `firstMaterialError` names the lowest-sequence cited observation of a `material` or `critical` finding, with its interface, operation and phase. Example: a bad validation response at sequence 3 precedes an incorrect final reservation at sequence 7. Repair the validation probe or oracle at sequence 3, then verify both observations after rerun. The interpretation copies engine outcomes and traces citations; it does not score claims or semantic checkpoints. A judgment checkpoint belongs in an anchored rubric criterion judged by a calibrated judge.

## Read held-out results

Read held-out results only from `gap-view.json`, whose held-out rows expose probe ID, class and the engine's reduced outcome object. Example: a row with `probeId: "P-021"`, `probeClass: "defect"` and `outcome.caught: false` means author a new development defect probe and inspect its oracle. Read `outcome.trialVotes` for the individual outcome states and `validCount` and `caughtCount` for the reduction. An `outcome: null` leaves the held-out cause undisclosed; reproduce its class failure in development and inspect those diagnostics. Keep held-out inputs and records closed, `corpus/held-out/`, a held-out baseline under `baseline/` and the items of `policy/judge-calibration.json` that label a criterion of the plan's `rubrics` included: a held-out-only step lives in the plan file `evaluation.json` names, so a repair edits `contract.json` for shared and development-only steps only and reads no byte of that file. Run the held-out partition only after the adopter reviews development evidence and confirms readiness; do not tune directly to a held-out answer.

## Map discipline and preflight checks to repairs

The discipline keys come from installed `DISCIPLINE_RULES`. The preflight keys come from the installed `preflight-verdict.schema.json`; a failed check invalidates the run.

| Discipline rule                | Concrete repair                                                                                                                                                                                       |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `success-indicator-separation` | Add a probe and oracle that read independent success evidence, not the target's success claim alone, and list that oracle in a behavior's `oracles`; an oracle no behavior lists leaves the gap open. |
| `whole-body`                   | Add one oracle whose direction and check both name every required response key pointer (a parent pointer does not count) and a mutation outside the keyword.                                          |
| `malformed-input`              | For each operation declaring a request key, bind `type-violating` on a step input and address that step with an oracle check; qualify a malformed request probe.                                      |
| `per-record`                   | Add a multi-record probe and per-record oracle evidence pointers.                                                                                                                                     |
| `sibling-cross-check`          | Add a probe whose sibling fields disagree and an oracle that compares them.                                                                                                                           |
| `omission-and-completeness`    | Add a missing-item probe and an oracle that checks the complete required set.                                                                                                                         |
| `state-change-read-back`       | Add a state mutation probe plus a read-back control and oracle.                                                                                                                                       |

The engine reads `malformed-input` coverage from the contract. A caught malformed-input probe alone leaves the rule unsatisfied until the planned input binding and addressed check exist for every relevant operation.

For example, an operation can declare a generic `requestKey` in `requestShape.stdin`:

<!-- example:request-shape -->

```json
{ "requiredKeys": [], "permittedKeys": ["requestKey"], "types": { "requestKey": "string" } }
```

A step invoking that operation can bind the key in `inputBinding.stdin`:

<!-- example:input-binding -->

```json
{ "requestKey": { "matcher": "type-violating" } }
```

An oracle check must address that step. These excerpts were validated in their respective contract locations with `eval-quality compile`.

| Preflight check        | Concrete repair                                                                        |
| ---------------------- | -------------------------------------------------------------------------------------- |
| `interface-present`    | Repair registry wiring and supply a real observation through the authorized interface. |
| `input-sensitivity`    | Add a probe pair whose changed input yields a distinguishable observation.             |
| `state-reset`          | Repair isolation and add a control that proves a fresh starting state.                 |
| `clean-control`        | Repair the clean control's target wiring or oracle until valid behavior passes.        |
| `seeded-faults-scoped` | Narrow the mutation to one adopter-owned target artifact and rerun its probe.          |
| `seeded-fault-fired`   | Choose a mutation that manifests on the signature channel and rerun its probe.         |

## Map an isolation violation to its repair

A confined run's audit lists each path a target opened outside what it was granted as an `observedMounts` entry of `runs/<invocationId>/trial-sets/<probeId>/isolation-manifest.json`. eval-quality records each one as an isolation violation, so `score` exits 3 (Invalid) with one `mount outside allowlist: <path>` reason per path. `run` applies the same check to its sealed trial sets, and `preflight` to the paths every one of its legs opened (the structural case, since every trial opens them too), and each exits 3 with the paths, so a setup `score` would reject stops there. A command named by its bare name and installed outside the workspace (`tea-skill-runner` under `node_modules` beside the evaluation folder) is the usual cause: make `target` a path inside `launch.root` (`node_modules/.bin/tea-skill-runner` over a copy workspace, or over a git workspace with `workspace.provision`), or keep the bare name and list the install's directories, and the bin directory that holds its link, in `systemPaths` of every entry that starts it. Read each path against this table, repair its cause and rerun from `check` as the loop below describes. Leave the manifest as the run wrote it.

| Observed path                                                                              | Cause                                                                                              | Concrete repair                                                                                                                                                                                                                                            |
| ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A toolchain, runtime, rules or cache directory the target should read                      | The entry does not declare it                                                                      | Add the directory to `systemPaths` of every entry that starts that target (`check` exits 10 when two entries over one target differ), run `check`, then rerun development.                                                                                 |
| A file the target should not read, such as a credential, another project or a dotfile      | The target or its input reaches beyond its task                                                    | Repair the target or the probe input so the target stops reading that path; declaring the path would hide the defect.                                                                                                                                      |
| A path under the evaluation folder, the project's git directory or the user's private root | The target searched for evaluation material, the git history or the runtime's private scratch root | Repair the target, since `systemPaths` cannot grant these and the audit lists every access to them; a target that must read the git directory opts out with `"confinement": false` and the adopter's recorded reason.                                      |
| A write outside the workspace                                                              | The target writes where a confined run allows no write                                             | Repair the target to write its workspace, `TMPDIR` or `HOME`, which the runtime provides; no registry field declares a writable path; a target that must write elsewhere or commit opts out with `"confinement": false` and the adopter's recorded reason. |

An empty `observedMounts` is evidence only where the audit ran and kept every report. A run that opted out (`run.json` records `"confinement": "opt-out"`) observes nothing, and on macOS the kernel's log can lose reports when the host is saturated, so rerun a surprising empty list on a quiet host. Linux's trace holds every traced syscall of the call, apart from file access through io_uring, and on macOS a process that reads after the trial's last read of the log goes unseen. On macOS `run.json`'s `observedMountsChannel` records each audited trial as `complete` (the log delivered every canary read the audit sent) or `lossy` with `canariesSent` and `canariesDelivered`, and the summary line of `run` names each lossy trial, so read an empty list from a lossy trial as unconfirmed and rerun it on a quiet host; a `complete` trial can still have dropped a single report between two canaries.

A Linux target whose call to a model provider or an outside HTTPS service fails to connect runs in a network namespace with a loopback and nothing else. List the host in `egress` on its entry with the addresses it resolves to, confirm `run.json` lists the entry under `egress`, read `egressRefusals` for the host and port the proxy refused, and rerun.
The shim announces the proxy in `HTTPS_PROXY` alone and the proxy reads `CONNECT` alone, so a client that opens no `CONNECT` tunnel (a plain `http://` request, a database driver) has no route, and such a target opts out with `"confinement": false` and the adopter's recorded reason.
A tunnel to a listed host and port carries whatever bytes the client sends, TLS or not, so a client that tunnels reaches a plain-HTTP gateway on the host's loopback that its entry lists.
A confined target cannot reach a host service through a socket file that exists when its call starts: a connection to the Docker socket (testcontainers) or to a database's Unix socket (a `.s.PGSQL.5432` file) answers `ECONNREFUSED` from a Bubblewrap target, since the runtime mounts an empty device file over each socket file it lists outside the call's own grants, and `EPERM` from a macOS Seatbelt target, since its profile denies every connection to a socket path outside the call's own grants. A socket file a host process binds after the call started is reachable wherever nothing masks or denies its path: under Bubblewrap anywhere outside the masks, on macOS only inside the granted paths and the bridge's shape beneath the private root, since seccomp cannot read a socket's path, a network namespace does not scope path sockets and AppArmor needs a profile that root loads. A target that needs one opts out with `"confinement": false` and the adopter's recorded reason. An exit 12 that names file-system confinement or its audit is a host or project condition: repair it as the run guide's `## Run confined` describes, and find each further cause (a failed step in building the target's private git repository, an observer that fails mid-run) in the [Evaluate CLI reference](https://github.com/bmad-code-org/bmad-method-test-architecture-enterprise/blob/main/docs/reference/tea-evaluate-confinement.md#file-system-confinement).

## Author, rerun and rescore

For an adopter installation, use the private package's binaries with `npm exec --prefix {tea_evaluations_folder}` as in the run guide. For TeA's own package, use `node cli/evaluate.js` and `./node_modules/.bin/eval-quality` from the repository root as in Stage 6. Keep the same engine installation throughout one run.

1. Name one gap, its engine outcome or failed check, and the cited observation or diagnostic in `{test_artifacts}/evaluate/<evaluationId>/gap-report.md`; record the current invocation ID.
2. Author the missing probe, clean control, oracle, rubric criterion or evidence pointer that addresses that gap. Record a refusal with reason if its channel cannot be observed.
3. Rerun `npm exec --prefix {tea_evaluations_folder} -- tea-evaluate digest --evaluation <evaluation-folder>` to refresh `corpus-index.json`, then `npm exec --prefix {tea_evaluations_folder} -- tea-evaluate check --evaluation <evaluation-folder>`, `npm exec --prefix {tea_evaluations_folder} -- eval-quality compile --in <evaluation-folder>/contract.json --out <evaluation-folder>/compiled-contract.json`, and `npm exec --prefix {tea_evaluations_folder} -- eval-quality seal --in <evaluation-folder>/contract.json --out <evaluation-folder>/sealed-brief.json`; halt and repair any nonzero exit. Under a `partitionPlan` `eval-quality compile` and `eval-quality seal` cover the development view alone (see Compile and seal in `contract.md`).
4. Rerun `npm exec --prefix {tea_evaluations_folder} -- tea-evaluate run --evaluation <evaluation-folder> --partition development`, then `npm exec --prefix {tea_evaluations_folder} -- tea-evaluate score --evaluation <evaluation-folder> --run <invocationId>` with the new completed invocation ID; read the new evidence and interpretation.
5. Record the repair, prior and new invocation IDs, before and after outcome, per-probe class component and first material error in the gap report. Record an adopter's decline with its reason. Repeat for remaining development gaps until closed or declined.
6. Once the adopter confirms readiness from the development artifacts, recorded gaps and the development `strength-aggregate.json`, run and score the held-out partition. Record each class's floor decision and basis from that aggregate; a `does-not-meet` class needs a development repair or the adopter's declined reason first, and an `absent`, `refused`, `mismatch` or `failed` aggregate blocks every class-wide claim until a rescore copies one. Read held-out only through `gap-view.json`, and open a new development repair for a missed held-out outcome.

## Decide target findings once

When the instrument gaps are closed or declined and the held-out partition is scored, present every target finding to the adopter once, in one list: each finding's summary, evidence, target artifact and proposed change. Ask for one decision per finding and record it as its `disposition`:

- `this-pr`: the change lands in this pull request.
- `new-pr`: the change gets its own pull request. Write the handoff from `assets/target-handoff.template.md` to `<evaluation-folder>/target-handoff.md` and set `handoff` to that path. It names the target, each finding with its evidence and proposed change, and the probe the next evaluation measures it with.
- `declined`: the adopter keeps the target as it is. Record the adopter's `reason`.

Leave no finding `undecided`. This is the only decision point for target changes in the pull request. Then make one pass, never a fix-and-rerun loop per finding, since every run is large:

1. Apply every `this-pr` change together, in the target artifacts the findings name.
2. Run the one development and held-out rerun the workflow already needs before the baseline, over the committed change: `tea-evaluate digest`, `check`, `run` and `score` as in `## Author, rerun and rescore`, then the held-out partition (or one run of both partitions).
3. Record each `this-pr` finding's `measurement`. `partitions` holds one entry per partition the evaluation has (or one `both` entry for a run of both): `before` is the scored run the finding came from (`null` when it came from a qualification or authoring record), and `after` is the rerun, the same for every `this-pr` finding. `probes` holds a receipt for each measured probe, the finding's own probe included: its `before` and `after` outcome (`caught`, `caughtCount`, `validCount` and the trial states as `votes`), copied from each score's evidence artifact, or from `gap-view.json` for a held-out probe. The receipts are committed, so the measurement stands when `runs/` is gone.
4. When `baseline/` holds an accepted run of the same partition, set the rerun beside it with `npm exec --prefix {tea_evaluations_folder} -- tea-evaluate compare --evaluation <evaluation-folder> --run <invocationId>` and copy each probe's relation into the gap report. `compare` refuses a run of another partition, so a held-out rerun beside a development baseline is read from the receipts.
5. Fill `## Net improvements` with the before and after numbers, copied and never computed.
6. Run `npm exec --prefix {tea_evaluations_folder} -- tea-evaluate check --evaluation <evaluation-folder> --ready` and repair every finding until it exits 0, before Stage 12.

The rerun can show a probe worse than before. A problem the rerun shows is never decided `this-pr`, since that would start another fix cycle, and `check` refuses one. Present it to the adopter with three choices: revert the change that caused it (record the reverted finding `new-pr` with the regression in its handoff, and rerun once over the reverted change to measure the rest), keep the change and hand the regression off as its own `new-pr` finding, or stop before the pull request and leave the evaluation open.

A `new-pr` change is measured by the next evaluation: its pull request reruns the evaluation, and `compare` against the accepted baseline reports the before and after.
