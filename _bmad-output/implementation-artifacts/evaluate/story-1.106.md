## Intent

**Problem:** Story 1.51 refuses a `partitionPlan` beside a waiver whose `condition` reads a development-only step, so an adopter who waives a known gap on a held-out request has no home for the waiver: `contract.json` would carry a condition that names the held-out step, and the development run would compile it.

**Approach:** A waiver belongs to the partition whose steps its `condition` reads (see "What a waiver names" below). Waivers in `contract.json` are in the development view, and in the held-out view unless the condition reads a development-only step. The held-out plan gains an optional `waivers` array for waivers only the held-out partition carries. `contractView` derives each partition's waivers at the one choke point, so the engine compiles, seals and records each view with the waivers that view holds.

## Boundaries & Constraints

**Always:** With no `partitionPlan`, and for a plan with no `waivers`, every committed fixture, baseline and replay stays byte-identical. A development run never opens the held-out plan. `check` findings name paths and IDs and never quote held-out plan bytes; a waiver is named by its ID only when the ID has the schema's shape `W-nnn`, otherwise by its index in `waivers`, and a step a plan waiver reads is named only when it is development-only. `schemaVersion` of the held-out plan stays 1 (the new field is optional). The engine's contract schema does not change.

**Never:** Partition evaluator mappings (Story 1.107), gameability answers (1.109) or designate a both-view oracle (1.110). Add a `partition` field to a waiver. Merge a plan waiver into a `contract.json` waiver. Invent an oracle or behavior link on a waiver, which the contract does not carry.

## What a waiver names

Read before the build; the AC text in `epics.md` said a waiver names the oracle or behavior it excuses, and the contract says otherwise.

- Representation: `contract.waivers[]` is `{ id W-nnn, rule, rationale, condition, approval, expiresAt }` (eval-quality `Waiver`, `schemas/eval-contract.schema.json`). Every part except `id` is a required key with a nullable value so that an incomplete waiver stays representable. `rule` names one of the seven AD-20 discipline rules as an opaque string; `condition` is "a machine-checkable context condition", a string or null (a null condition is a complete waiver). No field of a waiver holds an oracle ID, a behavior ID or a probe ID.
- What the engine does with a waiver: `compile` runs `checkWaiverCompleteness` over the contract and throws `waiver-incomplete` (exit 4) for a null `rule`, `rationale`, `approval` or `expiresAt` (`dist/core/compile/waivers.js`). Nothing else in compile reads a waiver, and `condition` is never parsed or resolved against the plan. `score` takes one caller-supplied waiver state (`none`, `applied-condition-met`, `applied-condition-unmet`, `expired`) that arrives already decided; `runScore`, the path the CLI takes, passes `'none'` and its comment says the contract declares no waiver the score reads (`dist/application/score.js`). A waiver is joined to a coverage gap by its `rule` string.
- What partitions a waiver: the steps its `condition` reads, by the rule a rubric criterion follows, with one difference in how the steps are read. `condition` is free text (`string|null` in eval-quality), so `stepsReadBy` reads every `/interactions/<stepId>` in the sentence (`CONDITION_STEPS` in `partition.js`), wherever it sits, the first and each later one, with or without a path after the step. The structured fields (`pointer`, `captured`, `evidence`) stay anchored to the start of their string, because their schemas make the whole string a pointer. A step ID has the shape `[a-z0-9]+(?:-[a-z0-9]+)*`, so a reference is whole when the next character is not an ASCII letter, a digit or `_`, and is not a hyphen followed by an ASCII letter or digit: `_` continues a word, so `/interactions/held-out-run_x` reads no step, and a non-ASCII letter ends a reference. The scan is a zero-width lookahead, so one reference does not consume the next and `/interactions/interactions/held-out-run` reads `interactions` and `held-out-run`. A null condition, or free text with no such pointer, reads none.
- AC rewrite: the Given and Then clauses named oracle IDs on a waiver, which the contract holds none of, so the criterion could not be met as written. They now speak of the steps the condition reads and name the step a view must never carry (`epics.md`, `test-design-epic-1.md`). The held-out waiver of the AC has a home in the plan's `waivers`, because a `contract.json` waiver that reads a held-out step would put that step's ID in the development view.
- No engine change is needed.

## Implementation Notes

- A waiver has one `condition`, a sentence that may name several steps, and one home; a condition that names a development-only step anywhere in it leaves the held-out view, whatever else it names: `contract.json` waivers are development (reading a development-only step), shared (reading a shared step or none); plan waivers are held-out. There is no stored `partition` field. The held-out view drops a `contract.json` waiver by the same `stepsReadBy` read that drops an oracle.
- A plan waiver may have a null condition. It then reads no step and is held-out by being in the plan.
- The step a `contract.json` waiver finding names is the adopter's own contract text. A plan waiver's finding names a step only when it is development-only, which the development partition already knows, because the plan's other steps are held-out text; any other step reads "a step the held-out view does not declare".
- `check` has no both-view rule over waivers (the engine reads none), so unlike rubrics nothing in `check` needs a `partial` flag and a contract error elsewhere cannot blame a waiver.
- Run directory artifacts carry the waivers of the view only: the run's `contract.json` and `eval-contract.json`.

## Design Notes

Alternatives turned down: a `partition` field on a waiver (the condition already decides, as a criterion's evidence does); an oracle or behavior reference on a waiver (the engine's schema is strict and the engine holds no such link, so TeA would invent a field eval-quality rejects); merging plan waivers into `contract.json` waivers (a waiver is a standalone record, so there is nothing to merge into); refusing a waiver whose condition reads no step beside a plan (it reads no partition's step, so every view may carry it).
