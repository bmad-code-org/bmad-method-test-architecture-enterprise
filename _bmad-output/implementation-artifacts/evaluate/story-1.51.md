## Intent

**Problem:** `run --partition` filters scored probes, but every arm executes the whole `contract.interactionPlan`, and the run directory, compiled contract, sealed brief, observations, trial records and replay carry every step's request and response. A development run can therefore launch and record a request meant only for held-out probes, and the authoring gap loop edits the same `contract.json` that would hold it.

**Approach:** Development-only steps stay in `contract.json`, named by `evaluation.json` `partitionPlan.developmentOnlySteps`. Held-out-only steps and their oracles live in a sealed held-out plan file under `corpus/held-out/`. One pure `contractView` derives each partition's contract at the single choke point in the pipeline, so launches, `contract.json`, `eval-contract.json`, the sealed brief and every artifact downstream carry only that partition's steps. With no `partitionPlan`, the source bytes pass through untouched.

## Boundaries & Constraints

**Always:** Leave every committed fixture, baseline and replay byte-identical when `partitionPlan` is absent. A development run never opens the held-out plan. `check` findings name paths and IDs and never quote held-out plan bytes. `partitionPlan` requires the deterministic evaluator. Do not change the engine's contract schema. Amend AD-9 and AD-22 and the Story 1.51 acceptance criteria in the same PR.

**Never:** Add a `partition` field to a plan step in `contract.json`. Add engine waivers. Partition rubrics, waivers or non-deterministic evaluator mappings (follow-up stories). Read held-out plan bytes in any development code path. Use Claude or a live model.

## Implementation Notes

- `contractView` (`cli/lib/evaluate/partition.js`) is pure. The no-plan and development views return the source `Buffer` itself; held-out and both views clone the parsed contract, drop (held-out only) the development-only steps and every oracle whose pointers read one, append the held-out steps and oracles, extend each behavior's `oracles` from `behaviorOracles`, and serialize `JSON.stringify(view, null, 2)` plus a newline. `loadContractView` reads the plan only for a partition that needs it. `selectPartition` replaces the inline selection in `run.js` and serves `preflight --partition` (exit 64 unknown, 10 empty held-out set).
- The view is computed once in `pipeline()` (`preflight.js`) after `check`; `prepare` receives `contract`, and the run directory's `contract.json` is `writer.write('contract.json', view.bytes)`, so `compile`, `seal`, every arm, the sealed brief, observations, trial records and `compare --accept`'s baseline all follow it. `run.js` reads `context.contract` for the evaluator layer. The plan-derived step ceiling and tool budget (`run.js` around :1231) read the view's plan unchanged.
- `checkEvaluation(folder, { partition })` lets a development run skip the held-out plan: `checkPartitionPlan` does not open it and `corpusIndexProblem(folder, { unread })` leaves it out of the hash comparison. That is stricter than the spec's code map (which only names the view derivation) and is what makes "a development run never opens the held-out plan" true of the whole development path; `check`, held-out and both runs read it.
- `check` validates the plan file against `held-out-plan.schema.json` with a path-and-message finding builder (`plainSchemaFindings`) that never prints an unexpected property's name, then runs `partitionPlanProblems`, then validates the derived held-out view against the engine's contract schema and maps each error back to the plan file's index. Messages carry paths and IDs only.
- The fixture's target is its own `bin/partition-target.js`, not the shared `verdict.js`: one gate covers each request, because a mutated target that rejects every request violates every oracle, which eval-quality records as `disagrees` and `ci` reads as an oracle-agreement failure. Defect IDs and mutations are per probe (`seeded-faults-scoped` fails when two defects share one effect). `test/lib/evaluate-story-121.js` `project()` takes `{ fixture, evaluation }`: the fixture directory is laid over the verdict project in place of its `evals/verdict`.

## Design Notes

The oracle problem decided the shape: the engine compile fails `unreachable-check-evidence` on an oracle that reads a missing step, so an oracle leaves a view with its step. Held-out plan oracles join `contract` behaviors through `behaviorOracles`; every behavior keeps at least one oracle in the held-out view. `check` cannot compile in-process (`test:evaluate-boundaries` forbids it under `cli/`), so an engine compile defect in the held-out plan surfaces at a held-out or both preflight; follow-up story covers `ci` compile and seal over each view.
