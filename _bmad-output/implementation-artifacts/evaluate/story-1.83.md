## Intent

**Problem:** Story 1.63 puts every Bubblewrap target in a network namespace of its own and lets an entry declare `"network": "host"` where it needs the network. A skill or agent target does, since an agent CLI calls its model provider. A `host` entry keeps the host's whole network and with it a route to the host's abstract Unix sockets, so the AD-8 gap stays open for exactly the targets that run an agent.

**Approach:** An entry lists the hosts its processes may reach (`egress`, items of `host`, `port` and `addresses`), and each Bubblewrap call of such an entry gets one route out, a runtime-owned proxy reached through the same mechanism as a started service's bridge, mirrored. The runtime serves an HTTP `CONNECT` proxy on a Unix socket in a private directory of the call, the call's status shim listens on a loopback port of the namespace and connects each connection to that socket, and the target starts with the port in `HTTPS_PROXY`. The namespace keeps a loopback and nothing else. The proxy tunnels a request only for a host and port an item lists, decided by eval-quality's `evaluateTarget`, and records each refusal with the host and the entry. An entry that lists no host has no proxy and reaches none. The registry field `network` is removed in the same change, so `check` refuses it, naming the entry and pointing at `egress`.

## Boundaries & Constraints

**Always:** The authorization is decided by eval-quality's `evaluateTarget`, as the HTTP port's requests are; TeA holds no copy of its logic. A host and port no item lists is refused before the name is resolved, and the connection goes to the address the decision was about. The proxy's socket and its authorization are private to the call and removed with it on every path, a signal that ends the run included. Any change to a Bubblewrap vector updates the byte-identity golden and the diff is read. The reference and the guides teach the authorization and no `"network": "host"`; `references/ci.md`, `SKILL.md` and `assets/evaluation-ci-plan.template.json` stay byte-identical (committed capture records pin their digests; Story 1.84 owns that edit). The skill's guides are edited through `/bmad-workflow-builder` Edit, headless. No eval-quality change, no new dependency, no native build, no new Linux package.

**Never:** a shared network namespace for a target, a route a target reaches without the runtime's decision, a default authorization of any host, a vendor-specific branch, an edit of the evaluation layer's vector, a claim in the reference no case backs.

**Decisions (build worker, owner-delegated):** the Decisions list below carries each choice with its reason and the Linux evidence.

## Decisions

1. **A proxy the target reaches through its environment.** A target in the namespace has no resolver and no route, so a connection to a provider's name cannot start without help. A transparent forward would need the provider's name in the namespace's `/etc/hosts` and a listener on port 443, which an unprivileged user namespace cannot bind (Bubblewrap drops every capability). `HTTPS_PROXY` is what an HTTPS client already reads: Node (24, with `NODE_USE_ENV_PROXY=1`, which the shim sets), `curl`, Python's `requests` and Go's `net/http` tunnel through it, and the target needs no change. The cost is stated in the reference: the shim announces the proxy in `HTTPS_PROXY` alone and the proxy reads `CONNECT` alone, so a client that opens no `CONNECT` tunnel (a plain `http://` request, a database driver) has no route.
   A tunnel to a listed host and port carries whatever bytes the client sends, TLS or not: the proxy never checks for TLS, so a client that tunnels (`curl -p -x "$HTTPS_PROXY"`) reaches a plain-HTTP gateway on the host's loopback that an item lists (review round 2; the build and review round 1 had said HTTPS only).
2. **`CONNECT` only.** A model provider is an HTTPS host, so a tunnel is what it needs. Forward proxying of plain `http://` requests would need an HTTP parser, request rewriting and a second decision path for a scheme nobody has asked for, so `HTTP_PROXY` is not set and a target's own plain-HTTP loopback traffic never meets the proxy. A `CONNECT` request that is not a request gets `400`, and any other method `405` naming `CONNECT`.
3. **The authorization is an eval-quality `ProbeTargetAuthorization` per item, decided by `evaluateTarget`.** The item is `{ host, port, addresses }`: the scheme is `https` and the method `GET` for every item (a tunnel shows the runtime neither; `evaluateTarget` needs both), the caps a tunnel does not use are their smallest (`maxRequestBytes` and `maxResponseBytes` 1, since the runtime cannot count an opaque stream), and `maxElapsedMs` is the entry's. `addresses` is eval-quality's own rule: a loopback, private or public address is allowed only when named. A provider's addresses change, so the guides tell the adopter to list what the host resolves to now and a refusal names the address that was not listed, so the repair is one line.
4. **Ask with no address first.** A host and port no item lists is refused before the name is resolved (`deploymentAccess` does the same for a deployment): a target cannot use the runtime's resolver to look up names of its choosing. Then the host resolves, every address is asked, and the addresses an item names are the ones connected to, in the order they resolved and the next when one cannot be reached, so a name that resolves differently a moment later reaches nothing new. Each authorization is asked alone, since eval-quality reports the first authorization's denial when none allows, which would hide an item behind another that lists a different host (review finding). A name that does not resolve is `502` and no refusal, since the entry authorized it.
5. **The proxy is in the runtime's process, the shim decides nothing.** The shim is a relay in the target's own namespace and the target can talk to it or around it; the one place a request is authorized is the runtime. A target that connects to the proxy's socket itself reaches the same proxy, and the directory is bound read-only, so it cannot replace the socket.
6. **The proxy's directory sits beneath the run's private parent and is bound at a synthetic `/dev` path.** The bridge directory sits in the temp directory because a grant beneath the private root would be hidden by the empty file system the sandbox puts over the root. The status file already shows the way out: bound at a path under `/dev`, which `--dev` makes a writable tmpfs. The proxy directory takes it, which puts it under the private parent the next run reclaims after a `SIGKILL` (Story 1.54), so the story's "removed on every path" holds for a kill too, which a case proves. Where the run has no private parent (a unit), the directory is made in the temp directory, and under `/tmp` when that leaves no room for a socket path (100 bytes). The authorization is a closure in the runtime and no file carries it.
7. **One proxy per call, outside the retry loop.** The command and tool-server mechanisms open the proxy once, run their attempts (a call made again over its own socket list, Story 1.82) against it, and close it however the call ends. The socket list excepts the proxy's directory, so Story 1.82's mounts never cover it.
8. **An entry that lists no host gets no proxy.** No listener, no variable, no refusal to record: a client with nothing to dial fails at once with its own error, and the guides name `egress` as the repair. A proxy that refused everything would name each host the target tried, which is useful, and it would also give every call of every entry a listener and a variable it does not need.
9. **`network` is removed.** The field was never released (Story 1.63 added it in the same unreleased window), and a `host` value keeps the gap this story exists to close. `check` refuses it with a message that names the entry and the replacement, from the schema error path (the generic "must NOT have additional properties" line is replaced by it, so there is one finding). `run.json`'s `hostNetwork` becomes `egress`, which lists what each entry may reach.
10. **`egress` applies to an entry that starts a process.** An HTTP entry that names its `port` starts nothing, so `check` refuses an `egress` there. Two entries that start one target must list the same `egress`, as they must list the same `systemPaths`, since a call finds its entries by its target; each entry's items become authorizations with its own interface ID and a refusal names every entry that shares the target.
11. **Bounds.** The proxy reads a head of at most 8 KiB within 5 s, resolves within 5 s, connects within 10 s, holds at most 256 open connections and 128 tunnels a call and keeps at most 50 distinct refusals a sandbox, counting the rest in `omitted`, so a target cannot grow the runtime's memory or descriptors through it.
    A host past 253 bytes (a DNS name's limit) is no request the proxy reads (`400`), and a refusal's detail is cut to 500 characters, so a call's record holds at most 50 refusals of a known size (review round 1: 60 requests with a host of 8,100 characters had made a report of about 0.8 MB a trial).
12. **`NODE_USE_ENV_PROXY=1` joins the variables.** Node reads `HTTPS_PROXY` only with it (Node 24); every other client ignores it. It is the one name the shim sets that is not a proxy spelling.
13. **Guides through the builder's Edit.** The four guides and the starter changed through `/bmad-workflow-builder` Edit (headless, the direction and the delta analysis recorded in the skill's `.memlog.md`): 0 critical, 0 high, 0 medium and 0 low new; the path-standards highs in committed files predate the edit. `references/ci.md`, `SKILL.md` and the plan template are byte-identical to `origin/main`; the `ci-registry` example there declares no network, and no test of Story 1.83's reads it for one.
14. **A revert proves each criterion.** The mechanism was reproduced first (an isolated entry reaches nothing, a `host` entry everything), then built and watched on Linux, then each criterion reverted once (Revert observations).
15. **One host grammar for the proxy and for `check` (review round 1).**
    The proxy's request grammar and `egressRegistryProblems` share one source (`HOST_SOURCE` and `isEgressHost` in `confinement-egress.js`): letters, digits, `.`, `-` and `_` up to 253 bytes, or a bracketed IPv6 address.
    `registry.js`'s `canonicalHost` accepted `*.example.com` and `a~b.example`, which no request can match, so `check` passed an item no request could use.
    `check` now names a wildcard as unsupported and any other host the proxy cannot read, beside the URL-spelling finding.
    `canonicalHost` stays for HTTP entries, whose hosts a URL names.
16. **A started server's port stays its own (review round 1).**
    The shim binds its egress listener on `127.0.0.1:0` in the namespace while the runtime chooses the started service's port on the host and passes it in the server's environment, so about 1 call in 7,000 collided and failed the server with `EADDRINUSE` as an infrastructure error.
    The call's request carries `listenPort` (a server told its port; a server that reports its port binds one the system gives it and cannot collide), `wrap` hands it to the shim as `--avoid <port>`, and `serveEgress` gives back a port in that list and asks again, up to 16 times.
    The fix is small, so it stays in this story and files no new one.
17. **The audit grants the proxy's directory nothing (review round 1).**
    The audit's read grants had listed the proxy's mount, and the pipeline case claimed the audit lists nothing for the proxy.
    The pipeline's server never opened a tunnel, so removing the grant (mutant M12) passed every case.
    The pipeline variant's server now tunnels once as it starts, and M12 still passes: the audit traces `open`-family calls, `readlink`, `execve` and the like, and the shim's `connect()` to the proxy's socket opens no path.
    The grant is dead code, so it is gone and the docstring says the audit lists no path for the proxy because no traced call touches one.
18. **The api fixture keeps its bytes (review round 2).**
    The pipeline server's tunnel had been written into `test/fixtures/evaluate-api/server/grader.js`, which changed the fixture's tree digest (`c189aaaf` to `f030c329`) that `baseline/run.json`, `baseline/probes.json` and the two probe records hold.
    The committed fixture is byte-identical to `origin/main` again, and `checkConfinedPipeline`'s `makeProject` writes the tunnel into its own copy of `server/grader.js` (`addTunnelToServer`).
    A run over a copy of the restored fixture digests to `c189aaaf` again.

## Limits the reference states, and the stories that follow

- The shim announces the proxy in `HTTPS_PROXY` alone and the proxy reads `CONNECT` alone. A client that opens no `CONNECT` tunnel (a plain `http://` request, a database driver such as `psql`) has no route: the namespace holds a loopback and nothing else, `check` passes the item and the call fails, and `egressRefusals` stays empty since the proxy never sees the connection. A tunnel to a listed host and port carries whatever bytes the client sends, TLS or not, so a client that tunnels reaches a plain-HTTP gateway or a database on the host's loopback that an item lists. A target whose client cannot tunnel opts out with `"confinement": false` and a recorded reason; the reference, the schema and the gaps guide say so.
- Plain `http://` through `HTTP_PROXY` is not served; no entry has asked for it.
- A killed run still leaves the call's temp, port and bridge directories in the temp directory, which sit outside the private parent: **Story 1.131**.
- The evaluation layer's processes keep every host socket and the host's network: **Story 1.88**.
