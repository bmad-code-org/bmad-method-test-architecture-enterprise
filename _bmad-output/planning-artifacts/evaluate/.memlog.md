- (decision) Target kinds eval-quality actually supports, derived from its five evaluate-*.md how-to guides, not from the input notes' unverified list: agent, skill, workflow, tool-use, ai-feature. Each maps to one of three interface kinds compile accepts: cli, api, mcp. web parses but is rejected at compile with unsupported-interface-kind.
- (decision) Kind mapping: agent (CLI-invoked program) -> cli. skill (instructions an agent loads, invoked via a command wrapper) -> cli, same kind as agent, narrower attribution question. workflow (ordered multi-step dependency) -> cli, api, or mcp depending on the target; workflow is an interaction-plan pattern (temporal clauses, captured bindings) layered on top of any interface kind, not a fourth interface kind. tool-use splits into two distinct systems under test: the calling agent (cli, reusing the agent-behavior shape) and the tool server itself (mcp, via createMcpAdapter). ai-feature (a product behind HTTP) -> api.
- (decision) TeA's own repository declares only cli interfaces today across all sixteen contracts (test-review, trace, eight fragment-selection, two routing). No api interface exists in TeA because BMad modules are developer tools driven by commands and files, not HTTP surfaces. No mcp contract exists in TeA yet either. This makes TeA itself the reference case for the agent/skill/workflow-over-cli shapes, and an intentional gap for ai-feature (api) and tool-use-server (mcp), which the Evaluate capability must still support for adopters outside TeA.
- (decision) eval-quality is fixed as the measurement engine: it validates/compiles, seals, preflights, and scores. It executes nothing and mutates nothing. The adopter (via the harness Evaluate scaffolds) plants the mutation by hand, runs the target twice (clean and mutated), and hands eval-quality the resulting sealed run records. This boundary is settled per the coordinator; not reopened.
- (decision) eval-quality-gates (the second binary) is a distinct, optional tool for deterministic repository governance (dependency licences, lockfile freshness, package boundaries, dependency-direction layering, documentation-claim/count/invocation drift). It is orthogonal to behavioral evaluation: per eval-quality's own docs, gates are explicitly not needed to evaluate an agent/skill/workflow/AI-feature/MCP server, and not needed to author or score a BEC. TeA already adopts all eight gates for its own repository hygiene (test:boundary, test:direction, test:doc-claims, etc. in package.json). Evaluate's CI enforcement policy (PASS/CONCERNS/FAIL/WAIVED/Invalid, the AD-21 verdict ladder and its exit codes) is built on eval-quality's own score command, not on eval-quality-gates. Gates may optionally be part of what Evaluate wires into an adopter's CI for repo hygiene, but they do not substitute for evaluation enforcement.
- (decision) Adopter definition, per coordinator: someone with an agent, skill, workflow, tool-use system, or AI feature who wants a running, strong eval. TeA evaluating its own skills (test/evals/, test/contracts/) is the first real adopter and proof target, and is also the only adopter with a worked example today: how-tea-is-tested.md itself names an Evaluate skill as proposed future work TeA does not yet have, with TeA's existing suites serving as the reference implementation until it ships.
- (decision) TeA's existing self-evaluation is extensive prior art, not a green field: ten skills each with a behavioral suite under test/evals/, sixteen generated Behavioral Evaluation Contracts under test/contracts/ (via tools/generate-contracts.js, never hand-written), 59 generated probes (via tools/generate-probes.js) across fifteen corpora, a three-exit-class discipline (0 pass, 1 quality failure, 2 environment failure) distinct from eval-quality's own six-exit-code ladder, a three-CI-tier policy proposal (deterministic every PR, smoke manual/scheduled, full-matrix manual/scheduled/release) in eval-quality-roadmap.md section 5, and a documented adapter (createCommandLineAdapter via test/lib/probe-targets.js) with a deny-by-default CommandTargetPolicy. Evaluate's capabilities describe the reusable authoring workflow this prior art built ad hoc, one skill at a time by hand; they do not describe inventing new primitives eval-quality or TeA's own harness already has.

- (capability) CAP-5 Oracle and rubric definition: define one designated oracle per behavior that a defect or gameability probe must discharge, and a rubric wherever judgment-heavy quality needs a judge's anchored scale. - (capability) CAP-6 Adapter and harness scaffolding: scaffold the target-specific runner command or MCP/HTTP wiring the target needs to be probed through eval-quality's supported interface kinds, and register it in an execution-target registry (logical name to real command, working directory, artifact map, budgets, permitted environment keys). - (capability) CAP-7 Mutation and rollback planning: define the controlled mutation each seeded-defect probe plants (target artifact, expected observable failure, rollback) and its manifestation witness. Success: every seeded-defect probe declares a targetArtifact and rollbackVerified, and its manifestation witness resolves both seeded-fault-fired and seeded-faults-scoped satisfied at preflight.
- (capability) CAP-8 Harness configuration generation: generate the scoring policy and the evaluator-configuration and isolation-manifest shapes the run needs. Success: the generated ScoringPolicy and configuration validate against eval-quality's published schemas.
- (capability) CAP-9 Pipeline orchestration: drive the adopter's evaluation through eval-quality's compile, seal, preflight, and score stages end to end for at least one clean-arm and one mutated-arm run (a twin run). Success: the mutated arm's seeded probe resolves caught in the resulting EvidenceArtifact.
- (capability) CAP-10 Gap interpretation: read a scored run's coverage gaps, unsatisfied discipline rules, and abstained or missed oracles, and translate them into a specific missing probe, control, or oracle rather than a bare verdict. Success: for a CONCERNS or FAIL verdict, Evaluate names the specific unsatisfied rule or missing evidence and proposes the specific probe, control, or oracle that would close it.
- (capability) CAP-11 CI enforcement wiring: wire the evaluation's continuous proof into the adopter's CI, deciding which checks run on PRs, merges, schedules, and releases, what blocks the pipeline versus surfaces as a warning versus is informational, and how target-behavior failure is told apart from evaluation weakness, repository-policy violation, and infrastructure or invocation failure. Success: the adopter's CI runs the compiled contract's deterministic checks (no model calls) on every PR at minimum, and the enforcement policy states, per check, whether it blocks, warns, or informs.
- (capability) CAP-12 Evidence publishing: define what evidence a CI run publishes for audit, observations, evidence artifacts, contract strength, verdicts, gate findings, and run metadata, including a recorded baseline for comparison across runs over time. Success: a completed CI run leaves a retrievable evidence bundle sufficient to answer what was measured and what it found, without re-running the evaluation.
- (constraint) eval-quality is the fixed measurement engine. Evaluate never reimplements contract compilation, sealing, preflight reduction, or scoring; it calls eval-quality's CLI or library for those stages.
- (constraint) eval-quality performs no mutation and executes no target. Evaluate, or the adopter harness it scaffolds, is responsible for planting the mutation, running the target, and producing the sealed run records and observations eval-quality scores.
- (constraint) Only cli, api, and mcp interface kinds compile. web is rejected under unsupported-interface-kind. Evaluate must map every target to one of the three supported kinds or decline; it cannot promise evaluation of a browser-driven web UI target today.
- (constraint) A defect signature cannot address a file the target wrote (refused under condition-artifact-channel-contract-local). Evaluate must plan a seeded probe's defect signature on exit-code or the descriptor-nominated stream/response-body, never on a bare artifact pointer, or record the probe as refused with a stated reason, following TeA's own precedent for test-review's gameability probe and trace's defect probes.
- (constraint) A behavior discharged by a defect or gameability probe must declare exactly one oracle (AD-40); a behavior spread across multiple oracles has no designated oracle and no probe naming it can score a caught defect. TeA's own contracts were originally grouped by severity and had to be split to one-oracle-per-behavior for this reason.
- (constraint) Versions float. Evaluate never pins eval-quality to an older release or proposes pinning it. TeA's own eval-quality.config.json already excludes eval-quality from lockfile-age freshness enforcement for exactly this reason, and Evaluate inherits that stance for every adopter it configures.
- (constraint) eval-quality-gates is not how behavioral-evaluation verdicts get enforced in CI. Evaluate's CI enforcement policy is built on eval-quality's own score verdict ladder (PASS/WAIVED/CONCERNS/FAIL/Invalid) and its exit codes, never on the separate, optional repository-governance gates binary.
- (constraint) Never evaluate a vendor dependency (the model, a framework). The system under test is always the adopter's own use of it, with the dependency held as a fixed condition of the run.
- (constraint) Public repository. No third-party individuals named, no employer-internal systems named, in the spec or any companion.
- (non_goal) Evaluate does not reimplement, fork, or wrap around any part of eval-quality's compile, seal, preflight, or score pipeline with equivalent TeA-owned logic.
- (non_goal) Evaluate does not evaluate the underlying model or vendor itself; the model is a fixed condition of every run, never the system under test.
- (non_goal) Evaluate does not support the web interface kind; eval-quality rejects it at compile today, so Evaluate cannot promise it either.
