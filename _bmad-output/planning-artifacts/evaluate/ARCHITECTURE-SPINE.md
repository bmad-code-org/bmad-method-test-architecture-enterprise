# Architecture Spine: Evaluate

## Design Paradigm

Ports and adapters around a fixed engine. The evaluation stack runs system under test, then the evaluation (the mechanism that runs the system, collects evidence and makes judgments), then the Behavioral Evaluation Contract, then eval-quality. TeA owns every layer above eval-quality, including each concern eval-quality states it leaves to the caller. Three layers of code, one direction of dependency:

- **Authoring layer:** the `bmad-testarch-evaluate` skill. Prompt content and the craft knowledge each stage needs, taught with worked examples. It inspects, asks, designs, chooses or builds the evaluation layer and writes declarative evaluation artifacts, then calls the runtime.
- **Runtime layer:** `tea-evaluate`, a bin in TeA's npm package over `cli/lib/evaluate/`. The only code that stages workspaces, launches targets, applies and rolls back mutations, records observations, drives the chosen evaluator and converts its judgments through one import contract, calibrates judges, builds and seals run records, digests the corpus, partitions held-out results, writes interpretation evidence and runs CI tiers.
- **Engine:** `eval-quality`, reached through its CLI and library. It compiles, seals, preflights, scores and measures strength. It runs nothing and mutates nothing.

Per-target adapters implement eval-quality's `EnvironmentProbePort` and plug into the runtime.

```mermaid
flowchart LR
  skill["bmad-testarch-evaluate<br/>(skill, prompts)"] --> artifacts["evaluation folder<br/>(declarative artifacts)"]
  skill --> runtime["tea-evaluate<br/>cli/lib/evaluate"]
  skill --> ciSkill["bmad-testarch-ci<br/>(edit mode)"]
  runtime --> artifacts
  runtime --> adapters["adapters<br/>cli · mcp · api port"]
  runtime --> evaluators["evaluation layer<br/>deterministic · sealed-brief agent · command · records"]
  evaluators --> bridge["bridge<br/>(MCP, one tool per brief interface)"]
  bridge --> adapters
  runtime --> engine["eval-quality<br/>CLI + library"]
  adapters --> engineTypes["eval-quality/adapters<br/>eval-quality/conformance"]
  harness["TeA test/ harness"] --> runtime
  ciSkill --> artifacts
```

`cli/` never imports `test/`. The skill never re-implements a runtime operation in prose. Nothing in TeA re-implements an engine stage.

### AD-6: The CLI decides every enforced verdict; the library only drives legs

- **Binds:** CAP-9, CAP-11
- **Prevents:** two verdict paths that disagree, or exit codes CI cannot reproduce by hand.
- **Rule:** The runtime calls `runPreflight` through a recording port, which is the only way to plan and drive preflight legs, and persists every observation. It also uses `resolveCheck`, `digestArtifact` and the conformance suites from the library. Every verdict CI enforces comes from the `eval-quality` CLI over persisted files: `compile`, `seal`, `preflight --observations`, `score` once per probe, and `aggregate-strength` once per `score` invocation (Story 1.45: the run-wide class strength and floor decisions are the engine's, copied into the score directory with TeA computing no rate, count or decision). The library's own preflight verdict is discarded. `preflight` receives the invocation's `--run-id`.
- **Amended 2026-10-01 in Story 1.68:** `score` holds the bytes of every input it verified (`cli/lib/evaluate/score-inputs.js`) and, after each CLI call, scores those bytes in process with the library's `runScore` and `serializeArtifact` and requires the staged artifact to equal the result byte for byte (an absent artifact must match a result with no artifact, whatever the call exited), after re-reading every input and naming the first that changed or appeared. The call's exit must be the one the held bytes give (the ladder's exit for a result, 4 for a structural failure, 5 for a fault, 64 for a private-storage manifest reference) and the `eval-quality:` lines on its stderr must be the ones the result prints (the qualification failures and, for an Invalid result, its basis); when the library refuses the held bytes only the exit is compared, since the CLI renders that error itself. The call's stdout and its other stderr text are not compared. The same holds for the `aggregate-strength` call of Story 1.45 (amended 2026-10-01): after it `score` re-reads every input, the run's policy included, reads the persisted evidence artifacts back and compares them with the bytes it copied, then aggregates the held bytes in process with the library's `aggregateStrength` and `serializeArtifact` and requires the staged aggregate to equal the result byte for byte and the call's exit (0, 4 for a refused set, 5 for a fault) to be the one the held bytes give; the comparison refuses and never supplies an aggregate, a floor decision or an exit. The in-process re-score compares and refuses, never decides: it supplies no verdict, exit code or artifact, and the CLI still decides every enforced verdict. `test:evaluate-boundaries` names `score-inputs.js` as the one file that may name `runScore`; `seal` and `preflightFromObservations` stay forbidden everywhere under `cli/`.
- **Amended 2026-10-02 in Story 1.69's build:** the call `run` makes for each attempt of a sealed-brief agent evaluator's qualification is held the same way.
  `scoreAttempt` reads the attempt's inputs (the contract, the preflight verdict, the evaluator configuration, the policy, the probe, the attempt's record and its isolation manifest) once through `holdAttemptInputs` in `cli/lib/evaluate/score-inputs.js`, from the run directory writer's own read (`writer.read`, held to the digest the runtime wrote), so an input that is not what the runtime wrote stops the run with exit 12 before any call; after the call it re-reads every input through the writer and makes the comparison `score` makes (`heldRefusal` in `cli/lib/evaluate/held-refusal.js`, which `score.js` calls too): the first changed input is named, the staged artifact must equal the in-process score of the held bytes byte for byte, and the call's exit and `eval-quality:` lines must be the ones the held bytes give, or `run` exits 12 and records no vote for the call.
  The staged bytes the comparison accepted are the ones copied and read for the vote.
  The comparison supplies no vote, exit or artifact.
  `test:evaluate-boundaries` names `held-refusal.js`'s `heldRefusal` as the one place that asks for the in-process score (`reproduce`) and `score.js`'s `heldAggregateRefusal` as the one that asks for the aggregate (`reproduceAggregate`), and refuses either call in `run.js` or anywhere else.
- **Leg routing:** a leg named by a defect's `manifestationWitness.legId` goes to the mutated copy of that defect's mutation, or to the pre-fix revision on the `historical` route. Every other leg goes to the pristine copy. Both copies stay live until preflight finishes. The registry builds each leg's authorization with `cwd` set to the copy the leg is routed to, from the per-operation staging `evaluation.json` declares. (Amended 2026-09-26 in Story 1.32: on the historical route's deployment route, a witness leg goes to the pre-fix deployment, its HTTP calls sent to the origins the probe names for it and no server started.)

The held-out plan's optional `waivers` array holds the waivers only the held-out partition carries, under waiver IDs `contract.json` does not use, and they join the held-out and both views only. `check` names a waiver that no view can reach by its waiver ID (a `contract.json` waiver that reads a step the development view lacks, a plan waiver that reads a development-only or an unknown step) and never quotes a plan waiver's text. eval-quality designates an oracle only for a behavior that names exactly one, so the both view scores a behavior with two oracles without one (Story 1.110). `ci` compiles `contract.json` for the stale-baseline comparison of a baseline under the view its partition ran; compile and seal over every view in `ci` follow in Story 1.108. **Evaluator mappings (amended 2026-10-04 in Story 1.107):** a `command` or `sealed-brief-agent` evaluator binds the keys it prints to oracles, behaviors and rubric criteria through `evaluator/mapping.json`, so the mapping follows the contract view (`mappingView` in `cli/lib/evaluate/partition.js`, beside `contractView`). A command evaluator receives `{ sealedBrief, observations }` and never the mapping; the mapping validates and converts its rows, is digested into `tea.evaluatorTreeDigest`, and for a sealed-brief agent is shown as the keys to judge (key, oracle and behavior IDs or criterion text and levels). A row of `evaluator/mapping.json` binds what `contract.json` declares, so it is in the development view, and in the held-out view unless that view drops the oracle or criterion it binds. The held-out plan's optional `mappings` array holds the rows for what only the held-out partition declares (`{ key, oracleId, behaviorId }` or `{ key, rubricId, criterionId, levels }`), and they join the held-out and both views only, so no held-out ID sits in a file the development run reads. A run's evaluator layer holds its view's mapping only, and its tree digest covers the view's mapping bytes in place of the file's, so the digest of a development run depends on no held-out row. `check` names a plan row by its place in `mappings` (never its key), a row of `evaluator/mapping.json` that binds what `contract.json` lacks by its key and IDs, and a plan criterion no key binds. A `records` evaluator reads no mapping: a record carries the oracles it disposes, the oracle and behavior of a finding, the criteria it scores and the plan steps its observations record (TeA names an observation `<label>-<stepId>`, as in `trial-2-shared-run`, and an observation holds the step's call inputs and every response channel), eval-quality's `score` ignores an oracle its contract lacks, and the rubric criterion check is the caller's, so under a `partitionPlan` `importRecords` refuses (exit 10, nothing copied) a record that names one the run's view does not declare, by where it sits in the record (`observations[3]`, `findings[1].observationIds[0]`) and never by the ID. An observation is admitted only when its ID is `<run label>-<a step the view declares>` or `<run label>-call-<n>` (the labels `trial-<n>`, `attempt-<n>`, `baseline`, `degenerate`, `mutated`, `re-pass-<n>`, written once in `records.js`), because a development run never opens the plan and cannot know a held-out step ID, and a citation only when the record holds the observation it names. `check` refuses a step named `call-<n>` under a plan, because its observation would look like an agent's chosen call. A command evaluator's files under `evaluator/` are read, executed and digested by the development partition, so such an evaluator derives a held-out key from its input and spells none. The held-out view's mapping is always serialized, so its bytes and the digests over them move only with the rows the view holds. A records evaluator beside a rubric and a `partitionPlan` is refused by `check`, because the harness's calibration judgments answer one labelled file for one contract.
- **Rejected:** computing held-out strength inside TeA, which would copy eval-quality's strength logic; the partition only groups outcomes the engine produced.

### AD-23: Where TeA's interpretation stops

- **Binds:** CAP-10, `score`, the skill's `gaps` stage
- **Prevents:** TeA re-implementing engine judgments under another name, or leaving the caller-side concerns eval-quality names with no owner.
- **Rule:** eval-quality leaves claim-to-evidence lineage, semantic checkpoint scoring, process and outcome separation, and first material error attribution outside the package. TeA covers what it legitimately owns and stops at the engine's boundary:
  - **Claim-to-evidence lineage:** TeA authors the evidence pointers every oracle and rubric criterion reads, requires every evaluator finding to cite observations and quote them, and traces each finding to its observations and pointers in `interpretation.json`. Whether a claim is supported is decided only by eval-quality's signature match and ingest conditions; TeA scores no claim.
  - **Semantic checkpoints:** a checkpoint that needs judgment is a rubric criterion with an anchored scale, judged by a calibrated judge (AD-22) and scored by eval-quality. TeA adds no checkpoint score of its own.
  - **Process and outcome separation, and first material error:** `evaluation.json` classifies each operation as `process` or `outcome`, keyed by the pair of its interface and its operation ID (`operationPhases: { interfaceId: { operationId: phase } }`), because an operation ID is unique only within its interface and the sealed observation names both (amended 2026-10-02, Story 1.42; `check` covers exactly the contract's pairs). `interpretation.json` partitions findings by the phase of each citation's pair, carries the citation's `interfaceId`, and names the lowest-`sequence` observation cited by a `material` or `critical` finding. Outcomes, verdicts and rates in the file are copied from the evidence artifact.
- **Rejected:** a TeA claim-support or checkpoint scorer, which would be a second verdict path (AD-6).
