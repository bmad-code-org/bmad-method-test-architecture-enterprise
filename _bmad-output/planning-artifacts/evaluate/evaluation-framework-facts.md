# Evaluation framework facts

Evaluate's evaluation layer is framework-neutral (AD-21). This file records verified facts about specific evaluation libraries so the stories that build and prove the neutral import contract (Stories 1.17, 1.19, 1.20, 1.23 and 1.26) start from checked ground. The frameworks here are worked examples from an open set: Evaluate's evaluation-layer guide teaches how to learn a framework absent from this file from its primary sources at run time (Stories 1.23 and 1.26), and the import contract never names a framework.

Every fact cites its source. A fact that could not be confirmed from a primary source is left out. Versions float (AD-13), so a story that relies on a fact re-checks it against the installed version and fixes this file when it has drifted.

## What an evaluation layer has to provide, in eval-quality's terms

Verified against `bmad-eval-quality` `origin/main` at `aa1b724` (the v4.0.0 release commit).

- eval-quality defines the evaluation as "the mechanism that runs or observes it and produces evidence plus judgments", and names "an eval framework, your own harness, a skill-specific evaluator, custom code you wrote" as evaluations (`docs/explanation/behavioral-evaluation-contracts.md:36-37`).
- It runs none of them. "Your harness owns active environment and evaluator execution: running the System Under Test (SUT), hosting services, dispatching active probe calls to verify measurability, running the evaluator model against the sealed brief, capturing interaction observations, and minting the sealed run record" (`docs/how-to/author-behavioral-contracts.md:133-134`).
- The evaluator's intended input is the sealed brief: "Hand `sealed-evaluator-brief.json` to `bmad-tea` to execute the task without seeing answer keys" (`README.md:204`). `seal` keeps the behaviors, the interfaces by name and kind, the bounds, one prose direction per oracle and the contract digest; the checks and the test data "have no place in a brief" (`docs/explanation/behavioral-evaluation-contracts.md:134-135`). The brief schema cannot carry the interaction plan, oracle checks or test data (`eval-quality-facts.md`, `src/core/schemas/sealed-evaluator-brief.ts:54-99`).
- A judge also runs outside the package: "Obtaining judgments from a model or human evaluator is the caller's responsibility" (`docs/how-to/evaluate-ai-feature-behavior.md:164`).
- What reaches `score` is a `SealedRunRecord` (`schemas/sealed-run-record.schema.json`). Required fields: `schemaVersion`, `parentDigest`, `revisionCount`, `runId`, `conditionArm`, `mode`, `trialIndex`, `contractDigest`, `sealedBriefDigest`, `evaluatorConfigurationDigest`, `evaluatorRecommendation` (`PASS`, `CONCERNS` or `FAIL`), `oracleDispositions` (`oracleId`, `disposition` of `held`, `violated` or `not-attempted`, `observationIds`, `note`), `findings` (a defect finding carries `findingId`, nullable `oracleId`, required `probeId`, nullable `behaviorId`, `severity`, `summary`, `confidence` in 0 to 1, at least one `observationIds` entry, `evidenceArtifacts`, at least one `quotedEvidence`), `observations`, `judgeResults` (`rubricId`, `criterionId`, integer or null `score`, `note`; empty when the contract declares no rubric), `actionsArtifact`, `isolationManifestArtifact`, `resourceUse` and `evidenceDisclosure`.
- Each observation carries `observationId`, `sequence` (positive, unique per record), `operationId`, `provenance` and every evidence channel (`callInputs`, `responseBody`, `responseHeaders`, `responseStatus`, `stdout`, `stderr`, `exitCode`, `artifacts`). `provenance` is `baseline` "for a pre-canned or deterministic test" or `evaluator-chosen` "for an action the evaluator selected" (schema description of `observations[].provenance`).
- A caught defect needs evidence: "The observation a finding cites has to match the defect signature the probe declared" (`docs/explanation/behavioral-evaluation-contracts.md:199-204`).
- eval-quality states what it leaves outside: "claim-to-evidence lineage, semantic checkpoint scoring, process and outcome separation, and first material error attribution" (`README.md:219`), and a generic judge-calibration platform among what is out of scope (`README.md:221`). Its tool-use guide states that it "does not evaluate whether an autonomous agent made the right reasoning choices or selected the right tools" (`docs/how-to/evaluate-tool-use-behavior.md:59`).
- eval-quality v4.0.0 is published and is npm `latest` (`npm view eval-quality dist-tags`, 2026-09-23). Its changelog section `[4.0.0] - 2026-09-23` records the HTTP target-policy export (#158) and trial-set scoring with `EvidenceArtifact` schema version 4 (#143) (`CHANGELOG.md`).

## AgentEvals

Sources: repository `github.com/langchain-ai/agentevals` at `main` `946ad15b9f2ce9bc9843edd2bb773bd07d78ca7e` (`README.md`, `js/src/index.ts`, `js/src/types.ts`, `js/package.json`); npm registry entry `agentevals`; PyPI entry `agentevals`; companion repository `github.com/langchain-ai/openevals` at `16b546bea58e3a62dabb79d2459cd90cc8ab0259` (`js/src/types.ts`).

- **What it is.** "A collection of evaluators and utilities for evaluating the performance of your agents, with a focus on agent trajectory, or the intermediate steps an agent takes as it runs" (`README.md:7`). Repository description: "Readymade evaluators for agent trajectories". Licence MIT (repository metadata; PyPI entry). For general evaluators the README points to the companion package `openevals` (`README.md:10`).
- **Languages and versions.** Python (`pip install agentevals`; PyPI 0.0.9, `requires_python >=3.9`) and TypeScript (`npm install agentevals @langchain/core`; npm 0.0.7) (`README.md:20,28`). The npm package declares peer dependencies `@langchain/core >=0.3.80` and `@langchain/langgraph >=0.2.46`, and dependencies `@langchain/openai`, `langchain`, `langsmith` and `openevals ^0.1.4` (npm registry entry). Its `exports` map has only `.` and `./package.json` (`js/package.json`).
- **Trajectory input.** A trajectory is "a list of OpenAI-style messages" (`README.md:38`): `user`, `assistant` (with optional `tool_calls`), `tool` messages (`js/src/types.ts`, `FlexibleChatCompletionMessage`).
- **Trajectory match evaluators (deterministic, no model).** `create_trajectory_match_evaluator` / `createTrajectoryMatchEvaluator` and `create_async_trajectory_match_evaluator` (`README.md:209`). `trajectory_match_mode` / `trajectoryMatchMode` is `strict`, `unordered`, `subset` or `superset` (`README.md:211`). `strict` requires matching message positions, roles, tool-call presence, tool names and parsed arguments; it compares multiple tool calls in one assistant message without regard to their order. `unordered` matches tool calls in any order; `superset` requires the reference's tool calls and allows extra ones; `subset` forbids tool calls beyond the reference (`README.md:216,358,526,663`, installed TypeScript implementation). Tool-argument equality is set by `tool_args_match_mode` (`exact` default, `ignore`, `subset`, `superset`) and per-tool `tool_args_match_overrides` (`exact`, `ignore`, a list of fields that must match, or a comparator function), with overrides taking precedence (`README.md:667-680`). The TypeScript root exports `trajectoryStrictMatch`, `trajectorySubset`, `trajectorySuperset`, `trajectoryUnorderedMatch` and `createTrajectoryMatchEvaluator` (`js/src/index.ts`).
- **Trajectory LLM-as-judge.** `create_trajectory_llm_as_judge` / `createTrajectoryLLMAsJudge` with prompts `TRAJECTORY_ACCURACY_PROMPT` and `TRAJECTORY_ACCURACY_PROMPT_WITH_REFERENCE` (`README.md:825-1050`, `js/src/index.ts`). It "takes the same parameters as `create_llm_as_judge` in `openevals`" (`README.md:1052`); documented parameters include `prompt`, `model`, `continuous` (a 0 to 1 float in place of a binary score, default false), `choices` (a list of floats naming the possible scores), `system` and `few_shot_examples` in Python (`fewShotExamples` in TypeScript) (`README.md:1054-1092`, installed TypeScript types). The quickstart judges with an OpenAI model and needs `OPENAI_API_KEY` (`README.md:31-36`). The Python async example passes a client as `judge` (`README.md`, "Python Async Support").
- **Graph trajectory.** For agents modelled as graphs, a graph trajectory value contains `{ inputs?, results, steps }`; the TypeScript evaluator call wraps that value as `{ outputs, inputs?, referenceOutputs? }`. LangGraph thread extraction utilities are `extract_langgraph_trajectory_from_thread` / `extractLangGraphTrajectoryFromThread` (`README.md:1094-1140`, installed TypeScript types). The TypeScript root exports `createGraphTrajectoryLLMAsJudge` and the extraction utilities (`js/src/index.ts`). The README's TypeScript example imports `graphTrajectoryStrictMatch` from `agentevals`, but at `946ad15` the root `index.ts` does not re-export it (it is defined in `js/src/graph_trajectory/strict.ts`) and the package `exports` map offers no subpath. This is a worked example of why the learn-on-the-go procedure executes a minimal example before relying on a documented API.
- **Result shape.** Evaluators return an object with `key` and `score`; `comment` is optional. A README example includes `{'key': 'trajectory_strict_match', 'score': False, 'comment': None}`. The TypeScript `EvaluatorResult` type is `{ key: string; score: number | boolean; comment?: string; metadata?: Record<string, unknown>; sourceRunId?: string }` (`openevals` `js/src/types.ts`, re-exported by `agentevals` `js/src/types.ts`).
- **Story 1.19 installed-version check, 2026-09-26.** TeA installed npm `agentevals@0.0.7` at the `latest` spec and `@langchain/core` at `latest`. The published package exports `createTrajectoryMatchEvaluator`; `createTrajectoryMatchEvaluator({ trajectoryMatchMode: 'strict', toolArgsMatchMode: 'exact' })({ outputs, referenceOutputs })` returned key `trajectory_strict_match` with a boolean score in both the matching and wrong-tool fixture cases. The strict scorer checks message positions and tool names and parses tool arguments as JSON for exact comparison. It compares multiple tool calls within one assistant message as a set, so a single-call fixture is used to make first-tool selection unambiguous. The package's peer dependencies are `@langchain/core >=0.3.80` and `@langchain/langgraph >=0.2.46`; its published package omits `license` metadata but includes an MIT `LICENSE` file. The installed package and its README confirm the remaining facts above; no model client is invoked by the strict evaluator.
- **Hosting.** Results can be logged to LangSmith through its pytest or Vitest/Jest integrations or its `evaluate` function (`README.md`, "LangSmith Integration"). Evaluate uses none of this: the evidence that counts is what reaches `score`.

## promptfoo

Sources: repository `github.com/promptfoo/promptfoo` at `main` `d59f045c4cda1193574380aae639d84380dbf5f2` (`site/docs/configuration/outputs.md`, `site/docs/configuration/expected-outputs/index.md`, `site/docs/providers/custom-script.md`); npm registry entry `promptfoo`.

- **What it is.** Repository description: "Test your prompts, agents, and RAGs ... Simple declarative configs with command line and CI/CD integration." Licence MIT; TypeScript; npm 0.123.1; binaries `promptfoo` and `pf`; `engines.node >=22.22.0` (npm registry entry). That engine floor is above TeA's `>=22.20.0` and at or below the Node 24 in TeA's `.nvmrc`.
- **Assertions over outputs already produced.** "If you already have LLM outputs and want to run assertions on them, the `eval` command supports standalone assertion files": outputs as a JSON string array (or objects with `output` and `tags`), assertions as a YAML list, run with `promptfoo eval --assertions asserts.yaml --model-outputs outputs.json` (`expected-outputs/index.md:664-703`).
- **Deterministic assertion types** need no model: among them `equals`, `contains`, `icontains`, `regex`, `starts-with`, `contains-any`, `contains-all`, `is-json`, `contains-json`, `javascript`, `levenshtein` and `not-` negations. Model-assisted types include `llm-rubric` and `factuality` (`expected-outputs/index.md:114-200,414-438`).
- **Script provider.** Any shell command can be a provider: `providers: ['exec: python chain.py']`; the script receives the rendered prompt, an options JSON string and a context JSON string, and standard output is the response `output` (`providers/custom-script.md`).
- **Result files.** `promptfoo eval --output results.json` (also `.jsonl`, `.csv`, `.yaml`, `.html`, `.junit.xml`, `.xml`) (`configuration/outputs.md:24-41`). The JSON structure is documented as `{ "version": 3, "timestamp", "results": { "prompts", "providers", "outputs", "stats" } }` (`outputs.md:72-84`). A JSONL row carries `testIdx`, `promptIdx`, `success`, `score`, `response.output` and `gradingResult` with `pass`, `score`, `reason` and `componentResults[]`, one entry per evaluated assertion with `pass`, `score`, `reason` and `assertion`; `gradingResult` and `componentResults` may be absent on error rows (`outputs.md:116-165`). JSON and other full exports include the eval `config`, with sensitive fields redacted on a best-effort basis (`outputs.md:277`). A mapping reads the output the installed version actually produced.
- **Network switches.** `PROMPTFOO_DISABLE_TELEMETRY=1` disables telemetry, `PROMPTFOO_DISABLE_UPDATE=1` disables the registry update check (`site/docs/configuration/telemetry.md`), and `promptfoo eval --no-cache` disables the result cache (`site/docs/configuration/caching.md`). A deterministic fixture run sets all three.
