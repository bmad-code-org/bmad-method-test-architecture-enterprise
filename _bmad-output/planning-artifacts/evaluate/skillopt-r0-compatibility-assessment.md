# SkillOpt R0: compatibility assessment for TeA Evaluate

Assessed 2026-10-14. Read-only source inspection. No model call, no paid inference, no SkillOpt run, no installation.

**Verdict: no-go for R1.** The upstream hooks fit a custom adapter without a fork. TeA has no per-task rollout seam, no eligible target corpus, no pre-dispatch spend control, and two partitions where the optimizer needs three roles. Details in sections 1 to 6.

### 1.2 What a TeA trial yields

- `tea-evaluate run` first qualifies every clean control in one baseline arm. If any oracle of the control's behavior is not `held`, the run stops with exit 11 and writes no trial set. A behavior that declares no oracle stops it with exit 10 (`run.js:429-444`). The per-oracle verdict is written to `qualification/<probeId>/baseline-pass.json` before the stop (`run.js:420-428`). The file keeps that name even when the verdict is violated, and the loop throws on the first failing control, so the verdicts of later controls are never produced (`run.js:410-444`).
- With `--before-state`, a control may fail its baseline only when its `noKnownDefectStatement` declares a known defect, and the run is marked never acceptable as a baseline (`run.js:418-419`, `:445`, `cli/evaluate.js:336-337`).
- Each sealed trial record carries `findings` and `oracleDispositions` per oracle with values `held`, `violated` or `not-attempted` (`cli/lib/evaluate/evaluator.js:39-43`, `run.js:1688-1699`).
- `mode` is always `contract-scoring` (`records.js:356`, comment at `:324-331`).
- Usage is reported per CLI request on stderr with the prefix `TEA_EVALUATE_USAGE_JSON:` (`cli/lib/evaluate/usage-report.js:5`, `cli/skill-runner.js:249-250`) and summed per trial set (`run.js:1646-1650`).

Refused outright, in the adapter and in a test:

- EQ strength vector, catch rate, comparability key, sealed verdict or recommendation relabeled as `hard` or `soft`. `evaluatorRecommendation` (`run.js:1697`) is a verdict on the evaluator's reading of one probe.
- Mutated, historical and gameability arm outcomes as `hard`. Those arms measure whether the evaluator catches a seeded defect.
- Any value outside `[0, 1]` or non-finite. Upstream does not check: `compute_score` casts and averages with a default of 0 for a missing key (`skillopt/utils/scoring.py:15-23`).
- `reference_text` of any selection or final item (`base.py:62-99`).

### Target eligibility

The planning document requires a low-risk task skill that is not an evaluator, with enough tasks for three disjoint roles (section 8).

- The committed evaluations are `test/evaluations/bmad-tea-evaluate` and `test/evaluations/bmad-tea-test-review`. Both are evaluator-class by this note's judgment: Evaluate evaluates other agents and skills, and test-review judges tests, which fits the planning document's exclusion of skills "whose primary job is evaluating" (section 8). No other skill under `skills/` has an evaluation folder (`test/evaluations/` holds these two). They hold 9 and 14 probe files, with 4 and 12 declared clean-control (`grep` for `"clean-control"` over each `probes/` directory).
- The tutorial fixture holds 3 probes (`test/fixtures/evaluate-tutorial/evaluation/probes`).
- Upstream draws a training batch of 40 tasks per step by default (`default.yaml:82`), a config value. The largest committed clean-control set is 12 probes.
- Criterion 5 depends on the evaluator-class exclusion above. Without it, the 12 clean-control probes of `bmad-tea-test-review` are the nearest candidate and still fall short of the 40-task default for three roles.
- No target, snapshot or editable region is named here. None qualifies today.

### Stop criteria, in force for any future scope

1. A rollout cannot return per-task `hard` without a change to `run.js` semantics.
2. A paid role cannot be reserved before dispatch.
3. The held-out suite is readable by the optimizer process.
4. The adapter needs more than four patched upstream bindings (a judgment threshold for a small adapter).
5. The target corpus cannot supply three disjoint roles.
6. Any TeA `contract-scoring` output is needed as `hard` or `soft`.

Criteria 1, 2 and 5 are met today. Criterion 3 is open: it depends on where the held-out folder lives, and no TeA control enforces placement (section 4). Criterion 4 is met for the exec backends (eight `chat_optimizer` bindings, section 4) and open for HTTP backends behind a metering proxy, whose behavior is unverified. Criterion 6 is not met: `hard` comes from oracle dispositions, and the EQ vector, catch rate and verdict stay out of it (section 2).

`ReflACTTrainer(cfg, adapter)` accepts a custom adapter with no upstream edit (`trainer.py:693-697`), and passing only the editable region as the skill string keeps every other byte out of reach (`skill.py:85-145`). This is the one part of the plan the code supports as written.

### Recommendation

Skip the integration. Keep the manual edit-and-retest workflow.

R1 is not proposed. R0 would be worth reopening only on all of these:

- An eligible task skill with a qualified evaluation of enough clean-control probes for three roles.
- A per-probe, clean-arm rollout seam in `tea-evaluate run`, approved as a deliberate TeA change.
- A shared pre-dispatch ledger from the MutEval workstream.
- A candidate identity lock, a final-data consumption record and a held-out placement the optimizer process cannot read (section 4).

## Answers to the five R0 questions

1. **Adapter calls the TeA path and consumes target-quality observations without mislabeling.** No without a change to `run.js`. A subprocess call of `tea-evaluate run` yields oracle dispositions from which `hard` derives (section 2) only when every clean control passes. A control failure collapses the batch to one bit and the CLI returns no per-probe result (section 1.3).
2. **Candidate for one region while the package, evaluator, permissions and anchors stay protected.** Yes upstream, by passing only the region as the skill string. TeA lacks the region-aware diff and checks anchors late (section 4).
3. **Small extension route to the real optimizer.** The Python route exists: build the config in memory and call `ReflACTTrainer(cfg, adapter)` (`scripts/train.py:852-856`). The CLI registry is hardcoded (`scripts/train.py:43-125`) and no JSON sidecar exists.
4. **Every paid call under the shared pre-dispatch budget.** No (section 4).
5. **Final data outside the search, identity locked, promotion under TeA and human control.** Placement can keep final data out. No identity lock or exposure record exists. Promotion stays manual because `compare --accept` cannot promote a skill.
